# Kysely patterns for Carshenas's data layer

Every snippet here was type-checked with `tsc` and linted with the app's ESLint configuration on 2026-09-27, against Kysely 0.29.6, node-postgres 8.23 and the schema in `db/migrations`, and every behaviour claimed was run against a migrated scratch database on PostgreSQL 18.6. The probe lived in one file under `src/server/db`; below, each piece is shown where it belongs. Kysely is 0.x and changes in minor releases: check Context7 or `https://kysely.dev/llms.txt` before using an API not shown here. Reasons and sources for each rule are in `craft.md`.

## Where the code lives

| File | What it holds |
|---|---|
| `src/server/db/database.ts` | the pool and `database()` (writes), `readDatabase()` (reads, typed read-only), `parseInt8` |
| `src/server/db/database-errors.ts` | `SQLSTATE`, `constraintViolation(error)` |
| `src/server/db/db-types.ts` | generated by `pnpm db:migrate`; never edited, never formatted |
| `src/server/db/sql-helpers.ts` | the named, tested `sql` fragments below; create it with the first one you need |
| `src/features/<feature>/server/<feature>-queries.ts` | reads on `readDatabase()`, returning DTOs |
| `src/features/<feature>/server/<feature>-mutations.ts` | writes on `database()` or on an executor passed in |

Lint enforces the boundary: only `src/server/db` imports `pg` or Kysely values (`sql`, `Kysely`, dialects); everywhere else may import Kysely **types** (`import type { Kysely, Selectable } from 'kysely'`, `import type { ReadonlyKysely } from 'kysely/readonly'`). SQL built by concatenation or template interpolation, and `sql.raw`, fail lint anywhere.

## Types the generated file gives you

- `DB` and one interface per table (`Listing`, `Source`, …), with column comments as JSDoc. Row types: `Selectable<Listing>`, `Insertable<Listing>`, `Updateable<Listing>` (type imports from `kysely`). A CHECK list is a union (`Selectable<Listing>['status']` is `'active' | 'sold' | 'expired' | 'gone' | 'removed'`), because `.kysely-codegenrc.json` overrides it; identity and generated columns are `ColumnType<…, never, never>`, so an insert that sets `id` or `content_sha256` does not compile.
- `int8` is `number` (the pool's parser throws beyond 2^53, verified), but only through our pool: a Kysely you build yourself (a test, a script) must pass the same `parseInt8` in the pool's `types`, or ids arrive as strings while the types still say `number` (verified). `numeric` is `string`; `timestamptz` is `Date` on the way out and `Date | string` on the way in; `bytea` is `Buffer`; `jsonb` is `JsonValue`.
- A `jsonb` value you insert is a `JsonObject` from `db-types.ts`, not `Record<string, unknown>`, which does not compile against a JSON column. node-postgres serialises a JavaScript **array** as a PostgreSQL array literal, not JSON: pass `JSON.stringify(array)` for a `jsonb` array (our payloads are objects, enforced by a CHECK).

## A read: `readDatabase()`, listed columns, a DTO

```ts
// src/features/listings/server/listing-queries.ts
import 'server-only';
import type { Selectable } from 'kysely';
import type { ReadonlyKysely } from 'kysely/readonly';
import { readDatabase } from '@/server/db/database';
import type { DB, Listing } from '@/server/db/db-types';
import { literal } from '@/server/db/sql-helpers';

type ListingStatus = Selectable<Listing>['status'];

export type ListingSummary = { id: number; url: string | null; status: ListingStatus; listedAt: string };

export async function findActiveListingsBySource(
  sourceId: string,
  limit: number,
  db: ReadonlyKysely<DB> = readDatabase(),
): Promise<ListingSummary[]> {
  const rows = await db
    .selectFrom('listing')
    .select(['id', 'url', 'status', 'listed_at'])
    .where('source_id', '=', sourceId)
    .where('status', '=', literal('active')) // a literal, so a partial index WHERE status = 'active' applies
    .orderBy('listed_at', 'desc')
    .orderBy('id', 'desc')
    .limit(limit)
    .execute();
  return rows.map((row) => ({
    id: row.id,
    url: row.url,
    status: row.status,
    listedAt: row.listed_at.toISOString(),
  }));
}
```

- `readDatabase()` is the same pool typed read-only: `readDatabase().insertInto(…)` fails with "not allowed with a read-only Kysely instance" at compile time (verified).
- The DTO is plain JSON-safe data in camelCase: Dates become ISO strings, nothing leaves `server/` as a row, never `selectAll()`. Anything cached with `'use cache'` is serialised, so a `Date` or a `Buffer` in it changes type.
- The default parameter lets a test or a transaction pass its own executor. To read your own uncommitted writes inside a write transaction, pass the transaction; the read-only type is a view of the same object (`trx as unknown as ReadonlyKysely<DB>`, which is what `readDatabase()` does and what Kysely's documentation shows).

## Keyset pagination

```ts
export type ListingPage = { items: { id: number; listedAt: string }[]; next: { listedAt: string; id: number } | null };

/** Newest first. The cursor keeps listed_at as PostgreSQL's own text, exact to the microsecond. */
export async function listingsPage(
  sourceId: string,
  pageSize: number,
  after: { listedAt: string; id: number } | null,
  db: ReadonlyKysely<DB> = readDatabase(),
): Promise<ListingPage> {
  const rows = await db
    .selectFrom('listing')
    .select((eb) => ['id', 'listed_at', eb.cast<string>('listed_at', 'text').as('listed_at_cursor')])
    .where('source_id', '=', sourceId)
    .$if(after !== null, (qb) =>
      qb.where((eb) =>
        eb(
          eb.refTuple('listed_at', 'id'),
          '<',
          eb.tuple(eb.cast<Date>(eb.val(after?.listedAt ?? ''), 'timestamptz'), after?.id ?? 0),
        ),
      ),
    )
    .orderBy('listed_at', 'desc')
    .orderBy('id', 'desc')
    .limit(pageSize + 1)
    .execute();
  const page = rows.slice(0, pageSize);
  const last = page.at(-1);
  return {
    items: page.map((row) => ({ id: row.id, listedAt: row.listed_at.toISOString() })),
    next: rows.length > pageSize && last ? { listedAt: last.listed_at_cursor, id: last.id } : null,
  };
}
```

- The comparison `(listed_at, id) < (…)` and the `ORDER BY` use the same columns in the same direction, with `id` as the unique tiebreaker; the index that serves it is `(source_id, listed_at DESC, id DESC)` (check with EXPLAIN that there is no `Sort` node).
- **A `Date` cursor loses microseconds.** Three rows a microsecond apart, paged one at a time with the `Date` from the previous page, returned an empty second page, because every remaining row compared later than the truncated cursor; the text cursor above returned all three (verified). Integer sort keys avoid the question; encode the cursor opaquely (base64 of the JSON) in the URL.
- Call `eb.refTuple` and `eb.tuple` on `eb`. Destructuring them (`({ eb, refTuple, tuple }) =>`), as Kysely's documentation does, fails `@typescript-eslint/unbound-method` here.

## Counts and lists of ids

```ts
export async function listingCountsBySource(db: ReadonlyKysely<DB> = readDatabase()) {
  return db
    .selectFrom('listing')
    .select((eb) => [
      'source_id',
      eb.fn.countAll<number>().as('total'),
      eb.fn.countAll<number>().filterWhere('status', '=', literal('active')).as('active'),
    ])
    .groupBy('source_id')
    .orderBy('source_id')
    .execute();
}

export async function listingsByIds(ids: readonly number[], db: ReadonlyKysely<DB> = readDatabase()) {
  return db
    .selectFrom('listing')
    .select(['id', 'url'])
    .where((eb) => eb('id', '=', eb.fn.any(eb.val([...ids]))))
    .execute();
}
```

- `count(*)` is `bigint`; with our parser it arrives as a number (verified), so type it `countAll<number>()`.
- `eb.fn.any(eb.val(ids))` compiles to `"id" = any($1)` with the array as **one** parameter (verified): one statement text for every list length, one `pg_stat_statements` entry. `.where('id', 'in', ids)` writes `in ($1, $2, …)`, whose text changes with the length; keep it for short fixed lists.

## A write: executors that compose, and transactions

```ts
// src/features/<feature>/server/<feature>-mutations.ts (the worker has its own, apps/worker/src/db/, since CS-32)
import 'server-only';
import type { Kysely } from 'kysely';
import { database } from '@/server/db/database';
import { constraintViolation } from '@/server/db/database-errors';
import type { DB, JsonObject } from '@/server/db/db-types';
import { jsonbSha256, literal, wasInserted } from '@/server/db/sql-helpers';

export type SeenListing = { sourceId: string; key: string; url: string; seenAt: Date };

const DAY_MS = 24 * 60 * 60 * 1000;

/**
 * Upsert on the natural key with a change guard: a known listing is rewritten only when its URL changed or its last
 * sighting is more than a day old (fetch_log keeps every visit), and last_seen_at never moves backwards. A row comes
 * back only when the listing was inserted or rewritten.
 */
export async function upsertListing(db: Kysely<DB>, seen: SeenListing) {
  return db
    .insertInto('listing')
    .values({
      source_id: seen.sourceId,
      source_listing_key: seen.key,
      url: seen.url,
      status: 'active',
      listed_at: seen.seenAt,
      last_seen_at: seen.seenAt,
    })
    .onConflict((oc) =>
      oc
        .constraint('listing_source_key_unique')
        .doUpdateSet((eb) => ({
          url: eb.ref('excluded.url'),
          last_seen_at: eb.fn<Date>('greatest', [eb.ref('listing.last_seen_at'), eb.ref('excluded.last_seen_at')]),
          // Seen again after expiring or disappearing: back on the market (listing_gone_not_seen_since insists).
          status: eb
            .case()
            .when('listing.status', 'in', ['expired', 'gone'])
            .then('active' as const)
            .else(eb.ref('listing.status'))
            .end(),
          delisted_at: eb
            .case()
            .when('listing.status', 'in', ['expired', 'gone'])
            .then(null)
            .else(eb.ref('listing.delisted_at'))
            .end(),
        }))
        .where((eb) =>
          eb.or([
            eb('listing.url', 'is distinct from', eb.ref('excluded.url')),
            eb('listing.status', 'in', ['expired', 'gone']),
            eb('listing.last_seen_at', '<', new Date(seen.seenAt.getTime() - DAY_MS)),
          ]),
        ),
    )
    .returning(['id', wasInserted])
    .executeTakeFirst();
}

// Composition: every function takes the executor; the caller owns the transaction.
export async function recordSighting(seen: SeenListing, payload: JsonObject): Promise<number> {
  return database()
    .transaction()
    .execute(async (trx) => {
      await upsertListing(trx, seen);
      const { id } = await trx
        .selectFrom('listing')
        .select('id')
        .where('source_id', '=', seen.sourceId)
        .where('source_listing_key', '=', seen.key)
        .executeTakeFirstOrThrow();
      // … the fetch_log row, and the extraction job enqueued with pg-boss's fromKysely(trx), go here …
      return snapshotFor(trx, id, seen.url, payload, seen.seenAt);
    });
}
```

- Name the arbiter with `.constraint('<name>')`: the constraint names are the contract, and a renamed column cannot silently change the target.
- The change guard is the `.where(…)` after `doUpdateSet`: an unchanged row is not rewritten and returns nothing. It must include every reason to write, here a listing that had expired or gone (it comes back to the market) and the day-old sighting too: guarding on the URL alone would leave `last_seen_at` at the first sighting, and `expireStaleListings` below would expire listings that are still for sale. First call `{ id, inserted: true }`; the same sighting again, or one an hour later, `undefined`; a sighting two days later or a new URL `{ id, inserted: false }` (verified on 2026-09-27).
- A `Transaction<DB>` is a `Kysely<DB>`, so functions typed `db: Kysely<DB>` run inside or outside a transaction. Never `await` anything but the database between the start and the end of the callback: fetch pages, call models and send messages outside it.
- The callback's thrown error rolls the transaction back and rethrows; its return value is `execute()`'s.
- Privileges are the second guard: run through the web app's pool, `recordSighting` fails with 42501 because `carshenas_web` may not insert listings (verified). Writes like this belong to the worker's role from CS-33.

## Get or create

```ts
/** Insert the snapshot, or find the identical one a concurrent writer inserted first. */
export async function snapshotFor(
  db: Kysely<DB>,
  listingId: number,
  url: string,
  payload: JsonObject,
  fetchedAt: Date,
): Promise<number> {
  const inserted = await db
    .insertInto('snapshot')
    .values({ listing_id: listingId, first_fetched_at: fetchedAt, url, canonical_version: 1, payload })
    .onConflict((oc) => oc.constraint('snapshot_content_unique').doNothing())
    .returning('id')
    .executeTakeFirst();
  if (inserted) return inserted.id;
  // A new statement: under READ COMMITTED it sees the row that won the conflict.
  const existing = await db
    .selectFrom('snapshot')
    .select('id')
    .where('listing_id', '=', listingId)
    .where('content_sha256', '=', jsonbSha256(payload))
    .executeTakeFirstOrThrow();
  return existing.id;
}
```

The same payload with its keys in another order returned the first snapshot's id (verified): `jsonb` stores keys in one canonical order, and the database computes the hash. `executeTakeFirstOrThrow` makes "the winner vanished" an error instead of a silent `undefined`.

## Insert, and map what the constraints refuse

```ts
export type AddSourceResult = { status: 'added' } | { status: 'invalid'; message: string };

const SOURCE_MESSAGES = {
  source_pkey: 'منبعی با این شناسه ثبت شده است.',
  source_id_format: 'شناسه باید با حرف کوچک لاتین شروع شود و فقط حرف، رقم و _ داشته باشد.',
  source_crawl_interval_floor: 'فاصلهٔ درخواست‌ها باید دست‌کم سه ثانیه باشد.',
} as const satisfies Record<string, string>;

function isSourceConstraint(name: string): name is keyof typeof SOURCE_MESSAGES {
  return name in SOURCE_MESSAGES;
}

export async function addSource(db: Kysely<DB>, id: string, intervalMs: number): Promise<AddSourceResult> {
  try {
    await db
      .insertInto('source')
      .values({
        id,
        origin: 'external',
        access_method: 'crawl',
        name_fa: 'منبع آزمایشی',
        base_url: 'https://example.ir',
        listing_visibility: 'public',
        min_request_interval_ms: intervalMs,
      })
      .execute();
    return { status: 'added' };
  } catch (error) {
    const violation = constraintViolation(error);
    // A NOT NULL violation carries a column instead of a constraint; this form maps only named constraints.
    if (violation && 'constraint' in violation && isSourceConstraint(violation.constraint)) {
      return { status: 'invalid', message: SOURCE_MESSAGES[violation.constraint] };
    }
    throw error;
  }
}
```

A duplicate id, an id breaking `source_id_format` and a 1,000 ms interval each came back as their Farsi result (verified). Unknown errors rethrow, and the action returns only the result, never the error. Outside a transaction this costs nothing extra; inside one, a failed insert aborts the transaction (25P02), so wrap it in a savepoint or restructure around `ON CONFLICT`. Test every entry of the message map.

## Claim a batch with SKIP LOCKED

```ts
/** Expire active listings unseen for 30 days, a batch per short transaction; parallel runs skip each other's rows. */
export async function expireStaleListings(db: Kysely<DB>, now: Date): Promise<number> {
  const cutoff = new Date(now.getTime() - 30 * 24 * 60 * 60 * 1000);
  return db.transaction().execute(async (trx) => {
    const batch = await trx
      .selectFrom('listing')
      .select('id')
      .where('status', '=', literal('active'))
      .where('last_seen_at', '<', cutoff)
      .orderBy('id')
      .limit(500)
      .forNoKeyUpdate() // the rows' keys stay, so references to them (fetches, snapshots) are not blocked
      .skipLocked()
      .execute();
    if (batch.length === 0) return 0;
    await trx
      .updateTable('listing')
      .set({ status: 'expired', delisted_at: now })
      .where(
        'id',
        'in',
        batch.map((row) => row.id),
      )
      .execute();
    return batch.length;
  });
}
```

The job queue itself is pg-boss (ADR-0011), which claims jobs this way internally; hand-rolled claims are for batch maintenance like this. Locking in `id` order keeps concurrent batches from deadlocking.

## `src/server/db/sql-helpers.ts`: the only home of `sql` fragments

```ts
import 'server-only';
import { sql, type Kysely, type RawBuilder, type Transaction } from 'kysely';
import pg from 'pg';
import { database } from '@/server/db/database';
import type { DB, JsonObject } from '@/server/db/db-types';

/**
 * A fixed value written into the SQL text instead of sent as a parameter, so PostgreSQL can prove a partial index's
 * predicate (status = 'active'). The type accepts literal strings and unions of them, never a plain `string`.
 */
export function literal<const T extends string>(
  value: T & (string extends T ? never : unknown),
): RawBuilder<T> {
  return sql.lit(value);
}

/** sha256 of a jsonb value, computed by the database exactly as snapshot.content_sha256 is. */
export function jsonbSha256(value: JsonObject): RawBuilder<Buffer> {
  return sql<Buffer>`jsonb_sha256(${JSON.stringify(value)}::jsonb)`;
}

/** Whether the row RETURNING describes was inserted (PostgreSQL 18: `old` is NULL for an insert). */
export const wasInserted = sql<boolean>`old.id IS NULL`.as('inserted');

/** Transaction-local setting: SET LOCAL takes no parameters; set_config(…, true) does. */
export async function setLocal(trx: Transaction<DB>, name: 'statement_timeout' | 'lock_timeout', value: string) {
  await sql`SELECT set_config(${name}, ${value}, true)`.execute(trx);
}

/** True when this transaction took the named lock; it is released at commit or rollback. */
export async function tryTransactionLock(trx: Transaction<DB>, key: string): Promise<boolean> {
  const { rows } = await sql<{ locked: boolean }>`
    SELECT pg_try_advisory_xact_lock(hashtextextended(${key}, 0)) AS locked`.execute(trx);
  return rows[0]?.locked === true;
}

export function isRetryableTransactionError(error: unknown): boolean {
  return error instanceof pg.DatabaseError && (error.code === '40001' || error.code === '40P01');
}

/** Runs work in a SERIALIZABLE transaction and retries it on a serialization failure or a deadlock. */
export async function inSerializableTransaction<T>(
  work: (trx: Transaction<DB>) => Promise<T>,
  maxAttempts = 5,
  db: Kysely<DB> = database(),
): Promise<T> {
  for (let attempt = 1; ; attempt++) {
    try {
      return await db.transaction().setIsolationLevel('serializable').execute(work);
    } catch (error) {
      if (!isRetryableTransactionError(error) || attempt >= maxAttempts) throw error;
      await new Promise((resolve) => setTimeout(resolve, Math.random() * 20 * 2 ** attempt));
    }
  }
}
```

What was verified:
- `literal('active')` is written into the SQL as `"status" = 'active'` with only the user value as a parameter; `literal(userInput)` with `userInput: string` does not compile (the parameter becomes `never`), while a union such as `'active' | 'sold'` does. Kysely's own `eb.lit()` refuses strings; `sql.lit` escapes quotes but must never see user input.
- `set_config('statement_timeout', '45s', true)` held inside the transaction and was gone after it; a second transaction could not take the advisory lock the first held.
- Two SERIALIZABLE transactions that each counted a source's listings and then inserted one (write skew) ended with 40001 for the second; `isRetryableTransactionError` recognised it, and the wrapper retried and returned on the next attempt. Each attempt must re-read everything: the callback runs again from the start.
- A controlled transaction (`db.startTransaction()…execute()`) whose `commit()` fails keeps its connection until you call `rollback().execute()`; without it `db.destroy()` hung. Prefer `transaction().execute(callback)`, which releases in every case.

Anything Kysely's builder does not express goes here as a named function with a test: text search (`@@`, `websearch_to_tsquery`, `ts_rank_cd`), trigram `%` and `similarity`, pgvector `<=>`, `now()` and `clock_timestamp()`, `RETURNING old`/`new`. `sql<T>` is an assertion, not a check: the helper's test is what proves `T`.

## See the SQL you send

- `CARSHENAS_LOG_SQL=1 pnpm dev` logs every statement with its parameters and duration (development only; parameters can be personal data).
- `query.compile()` returns `{ sql, parameters }` without running it: for review, paste the SQL into `pnpm db:psql -c "EXPLAIN (ANALYZE, BUFFERS) …"` with realistic values in place of `$n` (or `PREPARE` it and `EXPLAIN EXECUTE`), on data shaped like production.
- Kysely sends unnamed statements through node-postgres, so each is planned with its values; a fixed predicate that should match a partial index still needs `literal()`.
