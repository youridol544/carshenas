# Database craft: the rules a senior engineer follows, for Carshenas on PostgreSQL 18

Each rule is small; together they decide whether the data stays true, the pages stay fast and a migration never takes the site down. They come from the practitioners whose published work independently states most of the owner's own list (GitLab's database guidelines, Laurenz Albe, the PostgreSQL manual, Andrew Atkinson, Andrew Kane, Haki Benita, Brandur Leach, Nikolay Samokhvalov, Markus Winand), from the Stanford and CMU database courses, and from labs run on PostgreSQL 17 and 18 with pgvector 0.8.6. The research notes `docs/research/2026-09-27-postgresql-only-data-stack.md` and `docs/research/2026-09-27-database-craft.md` have the method; the IDs in brackets point to the appendix `docs/research/2026-09-27-database-research/`, which holds every quote, link and date: C-n in `integrity.md`, P-n in `performance.md`, H-n in `harness.md`, and "search §n", "access-layer" and "data-model" for those files. **[lab 2026-09-27]** marks what was measured against this repository's own schema while this skill was written.

**How to use it.** While designing, read the section for what you are doing. Before calling a migration or a query done, walk every section that applies; the measurable rules are marked **Measure** and are also rows in `review.md`. Examples use Carshenas's tables (`source`, `listing`, `snapshot`, `fetch_log`, and the planned `listing_price_event`, `valuation`, `saved_search`); money is written `_toman` until CS-2 fixes the unit.

**The owner's decisions of 2026-09-27** bind the rules marked "(owner)": (1) PostgreSQL only, no search engine unless a recorded trigger fires, never Elasticsearch (ADR-0011); (2) Kysely with plain SQL migrations under dbmate, types from kysely-codegen, Squawk (ADR-0012); (3) pg-boss as the job queue (ADR-0011); (4) PostgreSQL 18; (5) one `listing` table with an `origin`, Carshenas itself a source, origin-specific side tables (ADR-0013); (6) phone numbers as keyed HMAC hashes (ADR-0008 point 7); (7) an index on every foreign key by default, exceptions named in the migration; (8) vectors in the same database, `halfvec` side tables, exact search inside blocks first, HNSW only when measured, photos by 64-bit perceptual hash; (9) `bigint` identity keys, random hashed tokens for anything that grants access, UUIDv7 only for ids minted outside the database.

## Modeling

- **Write down what determines what before drawing tables.** Functional dependencies such as `trim_id → model_id → make_id`, `(source_id, source_listing_key) → listing_id` and `(trim, model year, day) → market value` tell you the keys, the tables and the constraints; every dependency whose left side is not a key is a decomposition or a constraint to add. Keep the list in `docs/design/data-model.md`. (Widom, Stanford CS145; Pavlo, CMU 15-445) [C-1]
- **Normalise to BCNF by default; keep a redundant column only when a constraint keeps it true.** A listing that stores both `trim_id` and `model_id` is guarded by a composite foreign key `(trim_id, model_id) → trim (id, model_id)`, so an extraction that puts a trim under the wrong model becomes a named violation instead of silent rot. Do not copy `make_id` beside `model_id` unless the same technique guards it. (Widom, Yang; PostgreSQL manual) [C-2]
- **Denormalise only with a derivation rule, a single owner and a rebuild path**: an expression or virtual generated column (computed on read; no user functions, no index in 18), a stored generated column (same-row immutable functions only), a materialized view refreshed by the worker (`CONCURRENTLY` needs a unique index), or a derived table owned by one job with `computed_at`, an algorithm version and an input hash. Never let a trigger and the app maintain the same value. (PostgreSQL manual, Kleppmann, Atkinson, Benita) [C-3]
- **One `listing` table for every origin, origin-specific facts in side tables** (owner). `listing.origin` is `external` or `native`, `source_id` is always set (Carshenas becomes the source `carshenas`), and the composite foreign key `(source_id, origin) → source (id, origin)` stops a native ad from claiming Bama or a crawled ad from claiming Carshenas. Fetches and snapshots belong to external listings; accounts, revisions and moderation to native ones. No polymorphic `owner_type`/`owner_id` (no foreign key possible) and no wide table of nullable origin columns. The native migration is additive: it drops `listing_only_external_for_now` and adds its tables. (GitLab, Fowler, Portas and Celko) [C-6, data-model]
- **Raw payloads in `jsonb`, everything you filter, join, constrain or value in typed columns.** `snapshot.payload` is `jsonb` with `CHECK (jsonb_typeof(payload) = 'object')`; mileage, model year, gearbox and price are columns. Never an entity-attribute-value table. (PostgreSQL manual, Heap, GitLab, Celko) [C-13]
- **Child tables, not arrays, for anything searched, constrained or referenced** (photos, body panels); an array only for a small list read and written whole. [C-14]
- **A closed set is `text` with a named CHECK; a set whose values carry data (labels, order) or grow is a lookup table** with a foreign key (makes, models, trims, cities, sources). Not enums by default: values cannot be removed from an enum; `docs/design/data-model.md` records any exception it makes. (Karwin, Kerstiens, Samokhvalov, Supabase) [C-10, H-27]
- **Observations are immutable and append-only; "current" is derived.** Snapshots, fetches, policy checks and price events refuse UPDATE and DELETE through `refuse_change_unless_purge()`; the current price is the latest event or a column updated in the same transaction as the event. (Kleppmann) [C-18, data-model]
- **A lifecycle is data**: `listing_status_transition` lists the allowed status changes per origin and `listing_status_guard` refuses the rest (SQLSTATE 23514, constraint `listing_status_guard`). A new state or transition is a migration that inserts rows. [data-model]
- **Leaving the market is a state with a time, not a deletion.** `status` plus `delisted_at` keep price history and valuations anchored; real deletions are hard `DELETE`s with cascades, done by a purge that honours a removal request. Soft-delete flags quietly disable foreign keys. (Brandur Leach, Samokhvalov, Christofides) [C-20, H-24]
- **A period is a range with a non-overlap constraint**: `tstzrange` plus `EXCLUDE USING gist (listing_id WITH =, during WITH &&)` (needs `btree_gist`), or PostgreSQL 18's `WITHOUT OVERLAPS` key; `[)` bounds. [C-19, C-28, H-13]
- **Native listings will keep an append-only revision trail** written by the same function that updates them; generic trigger audit only on rarely written admin tables. [C-21]
- **Use PostgreSQL's own features instead of designing for portability**: `ON CONFLICT`, partial unique indexes, exclusion constraints, generated columns, `RETURNING old/new`, pgvector. (Kerstiens) [H-28]
- **Decide retention per table when you create it**: how long snapshots keep their payload, when fetches are summarised, what a purge removes; partition an append-only table by month once it outgrows memory, so retention is `DETACH … CONCURRENTLY` and drop. [C-62]

## Where checks live

- **The database owns every invariant one row, one key or one reference must satisfy**, because it is the only layer every write passes through: the crawler, the extraction worker, Server Actions, a future seller app, a fix typed in `psql`, a migration's backfill. **The app repeats the checks a person can trip over**, earlier and in Farsi beside the field, and treats the database's rejection as the final word, translated into the same message. **Rules that span rows or depend on the outside world** (a seller's quota, a price implausible against the market value, "Divar is never crawled") live in code inside a transaction that makes them safe. It is not "simple checks in the database, complex ones in the app": it is invariants in the database, judgments and cross-row policies in the app, messages in both. (Samokhvalov, Jeremy Evans, PostgreSQL manual) [C-24, C-25]
- **Walk this list for every table**: types; NOT NULL unless unknown is a real, documented state; CHECK for ranges, formats, state lists and rules within one row (`delisted_at >= listed_at`, a price that must match its price type); UNIQUE for natural keys; a foreign key for every reference; EXCLUDE for periods. PostgreSQL 18's `NOT ENFORCED` only documents a rule you knowingly cannot afford; it is never a default. [C-24, C-7]
- **CHECK constraints are row-local and time-stable.** PostgreSQL assumes a CHECK gives the same answer forever and evaluates it only when the row is written, so a CHECK that calls `now()` or reads another table silently stops being true. Cross-row rules become a composite foreign key (a trim under its own model), a partial unique index (one running crawl per source), an exclusion constraint (non-overlapping periods), or a transaction that locks the parent row or runs SERIALIZABLE. (Laurenz Albe; PostgreSQL manual) [H-13, C-30]
- **A trigger that enforces a rule is a backstop, never the design**: it must lock what it reads, raise a named error, and come with a test. Ours raise SQLSTATE 23000 (append-only) or 23514 (lifecycle) with a named `CONSTRAINT`, so code maps them like constraints. The crawl-policy backstops (a crawl must cite the latest policy check; a 403, 429 or challenge stops the source in the same transaction) are cross-row triggers that arrive with the crawler in CS-6; CS-4 declared only the row-local rules. (Laurenz Albe) [C-30, data-model]
- **A trigger that judges a new row checks inserts AFTER INSERT and updates BEFORE UPDATE.** A BEFORE INSERT row trigger also fires on the row an upsert proposes, before PostgreSQL finds the conflict, so a re-crawl proposing `sold` for a known listing was refused as "new to sold" although the real change was "active to sold" (found by the CS-4 review). An AFTER INSERT trigger sees only rows actually inserted, and the update path runs the BEFORE UPDATE trigger with the real old row. Such a trigger qualifies the tables it reads and pins `SET search_path = public, pg_temp`. (PostgreSQL manual, "Overview of Trigger Behavior") [CS-4 review]
- **The app never pre-checks uniqueness as a guard.** A read before the write races: two sessions that both checked first inserted the same Bama listing twice. A friendly pre-check before a form submits («این نام قبلاً استفاده شده») is fine as a courtesy; the constraint still decides. [C-31, lab 2 in integrity.md]

## Writes and errors

- **Batch writes upsert on the natural key with a change guard** (owner rule for the crawler, extraction and revaluation):
  `INSERT … ON CONFLICT ON CONSTRAINT listing_source_key_unique DO UPDATE SET url = EXCLUDED.url, last_seen_at = greatest(listing.last_seen_at, EXCLUDED.last_seen_at) WHERE listing.url IS DISTINCT FROM EXCLUDED.url OR listing.last_seen_at < EXCLUDED.last_seen_at - interval '1 day' RETURNING id`. The guard names every reason to write: on the URL alone, `last_seen_at` would stay at the first sighting and the expiry job would retire live listings. A no-op `DO UPDATE` still writes a row version, and catching `unique_violation` leaves a dead tuple and burns an identity value per duplicate (1,000 failed inserts grew a heap from 72 to 136 kB). No row back means nothing changed. [lab 2026-09-27: new, unchanged and changed calls returned a row, nothing, a row] (Haki Benita, PostgreSQL manual) [H-1, C-31, C-34]
- **Tell an insert from an update with PostgreSQL 18's `RETURNING old`**: `old.id IS NULL` is true for an insert, and `old.<column>` hands the previous price to the price-event insert in the same round trip. `xmax = 0` works on 17 but is an implementation detail. [lab 2026-09-27] [C-33]
- **Deduplicate a batch before one upsert**: a row cannot be affected twice by one statement (SQLSTATE 21000). For a whole crawl page, one statement over the batch beats a round trip per row. [C-31]
- **Get-or-create: `ON CONFLICT DO NOTHING RETURNING` returns nothing for the existing row**, and even the popular "UNION ALL SELECT" form returns zero rows under concurrency. Read the winner in a new statement (under READ COMMITTED it sees the committed row), and treat a missing row after that as an error. PostgreSQL 19 adds `ON CONFLICT DO SELECT`. [lab 2026-09-27: a snapshot re-inserted with its JSON keys reordered found the first one] (Haki Benita) [C-32]
- **Insert-and-map for single writes a person triggers**: insert, catch, and map `constraintViolation(error)` (SQLSTATE plus constraint name) to a Farsi result; unknown errors rethrow. Budget for what a failed INSERT costs: it aborts the surrounding transaction, so every later statement fails with 25P02 unless a savepoint wrapped it, and a savepoint per row of a 500-row page is its own problem. [C-25, C-34]
- **Map by SQLSTATE and constraint name, never by message text**: 23503 foreign key, 23505 unique, 23514 check, 23P01 exclusion, 23001 a delete blocked by ON DELETE RESTRICT (PostgreSQL 18; not 23503), 23000 our append-only triggers; 23502 not null by column, because PostgreSQL 18 reports no constraint name for it (`constraintViolation()` returns `{ code, column }` then). One message map per feature, `satisfies Record<ConstraintName, string>`, with a test per entry. (PostgreSQL manual, node-postgres) [C-25, H-6]
- **Update only what changes**: `WHERE market_value_toman IS DISTINCT FROM $2`; compare hashes before sending updates; an UPDATE writes a new version of every row it matches. (Haki Benita: 10,000 rows touched instead of 1,010,000, 1.58 s to 0.30 s) [H-2]
- **Do not rewrite a bookkeeping column on every visit.** `last_seen_at` bumped on each crawl turns every upsert into a write; bump it only when older than about a day, or in bulk per crawl run, and never index it (see Indexes). [P-11, C-31]
- **MERGE is for a single writer synchronising a set** (the nightly revaluation of one day's values, under a singleton guard), never for concurrent upserts: MERGE racing an insert raised 23505. [C-35]
- **Once-only side effects carry an idempotency key under a unique constraint**: an alert delivery row inserted with `ON CONFLICT DO NOTHING RETURNING` is sent only if a row came back; a native submission stores its request hash and response per key. Telegram alerts are at-most-once: `pending`, `sending` committed before the call, `sent` after; a stuck `sending` row goes to a person. (Brandur Leach) [C-36, data-model]
- **Bulk backfills load into an UNLOGGED staging table, then merge**, and build a fresh table's secondary indexes after the load. (Haki Benita) [H-29]

## Transactions and concurrency

- **Know what READ COMMITTED gives you**: each statement sees a fresh snapshot, so read-modify-write in code loses updates (lab: two sessions each adding a listing to a duplicate group of 2 left the count at 3, not 4) and rules that read many rows see write skew. List every read-modify-write site and pick a fix. (PostgreSQL manual, Kleppmann's Hermitage, Pavlo) [C-37]
- **Fix read-modify-write in this order**: one atomic `UPDATE … SET x = x + 1`; a row lock (`SELECT … FOR NO KEY UPDATE`) in a short transaction; optimistic concurrency with an integer `version` column when a person's think time sits between read and write (never `updated_at`: a JavaScript Date drops microseconds); REPEATABLE READ or SERIALIZABLE with a retry when the decision reads many rows. [C-38, C-17]
- **Retry the whole transaction on 40001 and 40P01**, with jitter and a cap, rereading everything inside it. A controlled transaction (`startTransaction()`) whose COMMIT fails keeps its connection until you call `rollback()`. [lab 2026-09-27: a real write-skew pair failed with 40001; the pool hung until the failed transaction was rolled back] (PostgreSQL manual, Kleppmann) [C-39]
- **Lock with `FOR NO KEY UPDATE`** unless you delete the row or change its key: foreign-key checks take `FOR KEY SHARE`, so the stronger `FOR UPDATE` blocks every child insert. `NOWAIT` where an immediate «دوباره تلاش کنید» beats waiting (55P03); `SKIP LOCKED` for work claims. (Laurenz Albe) [C-40]
- **Claim work with `FOR UPDATE SKIP LOCKED` in a short transaction**, then do the work outside it and record the result in a second short transaction. The job queue is pg-boss (owner), which does this for you; hand-rolled claims are for batch jobs such as expiring stale listings. [lab 2026-09-27] (Brandur Leach) [C-41]
- **"Only one at a time"**: `pg_try_advisory_xact_lock(hashtextextended('revalue:' || day, 0))` for short sections (released at commit, safe under a transaction pooler); a lease row with an expiry for minutes-long work, which survives a crash by expiring. pg-boss has singleton queues. [C-42]
- **Transactions are short and hold no network call.** Fetch the page, call the model, send the Telegram message outside any transaction; write the results in one short transaction. Enqueue the follow-up job inside the transaction that wrote its rows (pg-boss `fromKysely(trx)`), so it commits or rolls back with them. `idle_in_transaction_session_timeout` is the safety net, not the design. (GitLab, Brandur Leach) [C-43, H-14, P-28]
- **Take locks in one global order** (for example by id: `WHERE id = ANY($1) ORDER BY id FOR NO KEY UPDATE`) and let the retry wrapper absorb the rare deadlock. [C-44]
- **pg-boss guardrails** (owner): with `notify: true` set a short backstop poll; do not rely on `singletonKey` outside a singleton or throttled queue; implement ADR-0008's stop-on-block as a per-source pause the handler checks before fetching; wrap `send()` in a helper keyed by queue name so payloads are typed; move to a slot table if several worker processes ever need a hard per-source cap. [access-layer]

## Keys, types and time

- **Keys are `bigint GENERATED ALWAYS AS IDENTITY`**, the natural key a named UNIQUE (owner). `integer` can run out and converting a busy primary key is a multi-release project; identity refuses hand-typed ids that would collide later. Tiny curated vocabularies use their text code as key (`source.id = 'bama'`, with a format CHECK). Identity values have gaps (every conflicting upsert and every rollback consumes one): never show ids as counts or use them to order events across tables. (Laurenz Albe, PostgreSQL wiki, Samokhvalov, GitLab) [C-4, H-25]
- **UUIDv7 (`uuidv7()`, built into 18) only for ids minted outside the database**, such as an object key the worker needs before its row exists; never UUIDv4 as a primary key; never an identifier as a secret. Anything whose possession grants access (a Telegram link token, a "stop alerts" link) is a random token of at least 32 bytes, and only its SHA-256 is stored. (RFC 9562, Atkinson, Samokhvalov) [C-5, data-model]
- **NOT NULL unless unknown is a real, documented state, and know three-valued logic**: `CHECK (price > 0)` accepts NULL; `x NOT IN (2, NULL)` matches nothing (use `NOT EXISTS`); `IS DISTINCT FROM` for change detection; unique constraints treat NULLs as distinct unless `NULLS NOT DISTINCT`. Make "no price" explicit with a price type column tied to the amount by a CHECK. (Winand, PostgreSQL wiki, Atkinson) [C-7]
- **Strings are `text` with a CHECK for the real rule** (`source_listing_key ~ '^\S{1,200}$'`, a URL scheme, a VIN pattern), never `char(n)`, and no invented 255s: a `varchar(n)` limit change takes a heavy lock, a CHECK can be replaced `NOT VALID` and validated. `char_length` counts the zero-width non-joiner. (GitLab, PostgreSQL wiki) [C-8, H-17]
- **Money is `bigint` in one named unit with a range check** (`asking_price_toman`, until CS-2 fixes the unit); never `money`, floats or `numeric(10,2)` (a 1.5 billion toman car overflows it). The database rejects the impossible (zero, negative, absurd); the implausible (ten times the market value) is the valuation step's job and goes to the review queue. (PostgreSQL wiki, Christensen) [C-9, H-25]
- **A rule shared by many columns can be a domain** (`toman_amount AS bigint CHECK (VALUE > 0)`), created with the tables that use it; change it `NOT VALID` then `VALIDATE`. Squawk discourages constrained domains; use them only on new tables. [C-11]
- **Instants are `timestamptz`; calendar days are computed in Asia/Tehran**: `(computed_at AT TIME ZONE 'Asia/Tehran')::date`, never `now()::date` in a UTC session (the server runs in UTC, `db/postgresql.conf`). Query ranges half-open (`>= start AND < next`), never `BETWEEN` on timestamps. Jalali dates exist only in the UI; model years are stored in both calendars with a CHECK that they agree (Gregorian minus solar is 621 or 622). (Laurenz Albe, PostgreSQL wiki, IANA) [C-16, data-model]
- **Know what the driver does**: `bigint` becomes a JavaScript number through our parser, which throws beyond 2^53 instead of rounding (`parseInt8` in `database.ts`); `numeric` stays a string until a DTO converts it on purpose; `timestamptz` becomes a `Date`, which keeps milliseconds only, so a µs value never round-trips; `now()` is the same for every row of one transaction (use `clock_timestamp()` where each row needs its own); a transaction needs one connection. [lab 2026-09-27: a thrown parser error rejects the query and leaves the connection usable] (MDN, node-postgres) [C-17, access-layer]
- **Normalise Persian text into a separate matching column and keep the original**: an IMMUTABLE normaliser (Arabic ي and ك to Persian ی and ک, three digit scripts to Latin, the zero-width non-joiner and tatweel handled) feeding a stored generated column created with the table. `citext` only folds case. (`search.md` has the function.) [C-12, search §2.2]
- **The database's own locale is the builtin `C.UTF-8`** (`db/bootstrap/create-database.psql`): text compares by code point, independent of the operating system's C library, so an OS or image upgrade can never silently reorder a text index. Persian alphabetical order, where a page needs it, is `ORDER BY name_fa COLLATE "fa-x-icu"` in that query. [lab 2026-09-27: code-point order put هیوندای before پژو; `fa-x-icu` gave «بنز پژو تویوتا چری ژیان کیا گلف هیوندای»]
- **Order the columns of a big table by alignment when you create it** (8-byte, then 4, 2, 1, then variable length); never rewrite a table for it. (GitLab, Samokhvalov) [C-15]

## Names and documentation

- **Tables are singular English nouns from the glossary** (`listing`, `source`, `fetch_log`), columns lower_snake_case, foreign keys `<entity>_id`, instants `_at`, days `_on`, units as suffixes (`_toman`, `_km`, `_ms`, `_days`), booleans `is_`/`has_` and rare. Never transliterated Farsi. (PostgreSQL wiki, GitLab) [C-22]
- **Every constraint and index is named `<table>_<meaning>_<kind>`**, so a violation reads as the rule it guards: `listing_source_key_unique`, `listing_source_fk`, `source_crawl_interval_floor` (a CHECK: any meaningful suffix except `_check`), `listing_status_transition_pkey`, `crawl_run_source_started_idx`, a unique index `crawl_run_running_per_source_unique`, a future `promotion_no_overlap_excl`. Our suffixes differ from PostgreSQL's automatic ones (`_fkey`, `_key`, `_check`) on purpose, so an unnamed constraint stands out and the catalog test catches it. Names stay under 63 bytes (PostgreSQL truncates silently). (PostgreSQL manual: "constraint names like col must be positive can be used to communicate helpful constraint information to client applications") [H-6, C-22]
- **COMMENT ON every table and on every column whose meaning, unit or provenance is not obvious.** kysely-codegen turns comments into JSDoc, so the next agent reads them in `db-types.ts`. An exception to a rule is a comment too: `COMMENT ON CONSTRAINT listing_source_fk ON listing IS 'unindexed: …'`. [C-23]

## Migrations

- **Plain SQL, one concern per file, from `pnpm db:new`** (owner). dbmate runs each file in one transaction and records only its version: it never notices an edited migration, so `pnpm db:lint` fails when a migration on `main` was edited or deleted. A correction is always a new migration. [C-52, access-layer]
- **Every transactional migration sets `lock_timeout` and `statement_timeout`** at the top of both sections (`SET LOCAL`, the house template), and a lock timeout (55P03) is retried rather than waited out: a waiting `ALTER TABLE` queues every later query on the table behind it, reads included. The migrate role also carries `lock_timeout = 5s`. (Samokhvalov, Squawk, depesz, GitLab, Atkinson: up to 50 attempts with jittered backoff on his busiest table) [C-46, H-3]
- **No `IF [NOT] EXISTS` in versioned migrations**: it lets a migration "succeed" against a database that differs from what it expects. `pnpm db:check` proves every file do-undo-do on a scratch database, so every down section must work too; production fixes forward. Squawk's `prefer-robust-stmts` is excluded for this reason. (Samokhvalov) [H-4, C-52]
- **On a table that has rows, add a constraint `NOT VALID` and `VALIDATE` it in a later migration** (an ordinary transactional file: only `CONCURRENTLY` needs `transaction:false`; Squawk flags the two in one file). Measured locks: `ADD CHECK … NOT VALID` briefly holds ACCESS EXCLUSIVE, `ADD FOREIGN KEY … NOT VALID` SHARE ROW EXCLUSIVE on both tables, `VALIDATE` only SHARE UPDATE EXCLUSIVE, and only if it runs in a separate transaction. NOT NULL on 18: `ADD CONSTRAINT listing_model_id_not_null NOT NULL model_id NOT VALID`, then `VALIDATE CONSTRAINT` (pg-aiguide's `SET NOT NULL NOT VALID` is a syntax error). (PostgreSQL manual, GitLab, Squawk) [H-5, C-48]
- **Build indexes `CONCURRENTLY`, each alone in a `-- migrate:up transaction:false` file** whose only other lines are the comments `-- squawk-disable-assume-in-transaction` and `-- squawk-ignore require-lock-timeout, require-statement-timeout`. No `SET` lines: PostgreSQL runs a multi-statement string as one implicit transaction, so `SET lock_timeout …; CREATE INDEX CONCURRENTLY …` fails with 25001 even under dbmate's `transaction:false` (dbmate logs "Applied" first, then the error, and records nothing). The lock timeout comes from the migrate role (`lock_timeout = 5s`); a build needs no statement timeout; build settings such as `maintenance_work_mem` go on the connection for that run (`dbmate --url "$DATABASE_MIGRATE_URL&maintenance_work_mem=1GB" up`). [lab 2026-09-27: each of these reproduced with dbmate on PostgreSQL 18.6] A failed concurrent build leaves an INVALID index: find it with `SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid`, drop it concurrently, retry. Unique constraints: `CREATE UNIQUE INDEX CONCURRENTLY`, then `ADD CONSTRAINT … UNIQUE USING INDEX`. On a table created in the same file, a plain `CREATE INDEX` is right. [C-49, P-13, access-layer]
- **Change a shape by expand, migrate, contract**: add the new column, write both, backfill in batches, validate constraints, switch reads, stop writing the old, drop it in a later release. Never rename or drop in one step once the site is live (from CS-23). (Jacqueline Xu at Stripe, GitLab, Atkinson) [C-47]
- **Know what rewrites a table**: `ADD COLUMN … DEFAULT now()` does not rewrite and gives every old row the migration's own time (so backfill "first seen" from the data instead); a volatile default (`clock_timestamp()`, `gen_random_uuid()`) rewrites; `varchar` to `text` does not; changing a stored generated expression rewrites under an ACCESS EXCLUSIVE lock (300,000 rows took 28.8 s). [C-50, search §1.2]
- **Backfill in small committed batches outside the migration**, over a key range whose predicate makes reruns harmless, recording the last id so a crash resumes. [C-51]
- **Extensions.** `pg_trgm`, `btree_gist`, `fuzzystrmatch` and `unaccent` are trusted, so a migration run as the owner can create them; `vector` and `pg_stat_statements` are not, so a superuser creates them in `db/bootstrap` and on the server, before the migration that needs them. When a migration adds an extension, load the matching PGlite module in `schema-test-database.ts` (`@electric-sql/pglite/contrib/<name>`; pgvector is the separate `@electric-sql/pglite-pgvector`). [lab 2026-09-27: `CREATE EXTENSION vector` as `carshenas_migrate` failed with "Must be superuser"]
- **A new table is closed to the app**: grant `carshenas_web` (and, from CS-6, `carshenas_worker`) exactly what each needs in the same migration; the read-only role gets SELECT through the default privileges. [C-58]

### Migration checklist

Before `pnpm db:migrate`, for every file:

1. One concern; name from `pnpm db:new`; a comment under `-- migrate:up` says what and why, with the task or ADR.
2. `SET LOCAL lock_timeout` and `statement_timeout` in both sections of a transactional file; a `transaction:false` file holds its one statement and the two Squawk comments, nothing else.
3. Every constraint and index named `<table>_<meaning>_<kind>`; every new table and non-obvious column commented; units in names.
4. Keys `bigint` identity or a text code; foreign keys `bigint` with a deliberate ON DELETE (RESTRICT for curated parents, CASCADE for components and purgeable observations, SET NULL for optional derived links); an index leading with each foreign key's columns, or an `unindexed:` comment with the reason.
5. Every invariant a row, key or reference must obey is declared; cross-row rules are keys, partial unique indexes or exclusion constraints.
6. On a table with rows: `NOT VALID` then `VALIDATE` in a later (transactional) file; `CONCURRENTLY` alone in a `transaction:false` file; no volatile default; no rename or drop in one step; no table rewrite without a plan.
7. Grants for each application role; nothing wider than the role needs.
8. Append-only tables get the `refuse_change_unless_purge()` trigger; a lifecycle gets transition rows, not a CHECK that lists pairs.
9. A down section that really undoes the up section (proved by `pnpm db:check`).
10. After `pnpm db:migrate`: the codegen overrides the schema tests ask for, a constraint test per new rule, `docs/design/data-model.md` updated, all committed together.

## Indexes

- **Index a measured query, not a column** (owner rule 7 is the one exception, below). Find the query (top of `pnpm db:top-queries` by total time, or a page path over budget; GitLab uses 100 ms), read its plan on realistic data, design one index for the query family, prefer extending an existing index, build it concurrently, compare buffers before and after, price the write cost, recheck its scans a week later. **Measure** (GitLab, PostgreSQL manual, Samokhvalov, Winand) [P-1]
- **Every foreign key gets an index that starts with its columns, by default** (owner). Deleting 20 listings with unindexed children took 4,481 ms against 1.25 ms indexed, and the plan hid it in a `Trigger for constraint … time=` line. A unique or primary key that starts with the foreign key counts. An exception is a `COMMENT ON CONSTRAINT … IS 'unindexed: <reason>'` (for example: an existing index serves it through its leading column; the referencing table has a handful of rows). [P-9, H-7]
- **Know what a B-tree serves**: `=`, ranges, `IN`/`= ANY`, `IS NULL`, sort order with `LIMIT`, prefix `LIKE` only with the `C` collation or a pattern operator class. Not a function or cast on the column, a leading wildcard (pg_trgm), `<>`, or a condition only on a non-leading column, which PostgreSQL may still "use" by reading the whole index (1,469 buffers for 171 rows, a healthy-looking plan unless you read the buffers). PostgreSQL 18's skip scan helps when the leading column has few values. (PostgreSQL manual, Winand) [P-2]
- **Equality columns first, then one range column, or the sort columns** (Winand): `(model_id, price_toman)` read 5 index pages, `(price_toman, model_id)` 758. Only the first range narrows the scan. [P-3]
- **Let the index deliver the order**: `(model_id, deal_score DESC, id DESC) WHERE status = 'active'` serves "best deals first" as an index scan under `LIMIT` with no `Sort` node; the direction and NULLS placement must match the `ORDER BY` exactly (or be its exact reverse), and the unique tiebreaker `id` must be in both. `Sort Method: top-N heapsort` in a plan means the index did not provide the order. **Measure** [P-4, access-layer]
- **The LIMIT trap**: for "one model, sorted by price, first 20" the planner may walk the price index and filter, assuming the model is spread evenly; car prices, mileage and years are tied to the model, so «بنز E250» cheapest-first discarded 761,721 rows (754 ms). Composites that lead with the equality column fixed it (0.09 ms). Test sorts against skewed data, never uniform data. **Measure** [search §3.3]
- **Partial indexes for the hot subset, and the predicate is a literal in the SQL text**: the partial index on active listings was 1.6 MB against 11 MB for all rows. The query must repeat the predicate, and a builder that sends `status = $1` cannot prove `status = 'active'` under a generic plan; write it with `literal('active')` (`kysely.md`). (PostgreSQL manual, Haki Benita) [P-5, H-21, access-layer]
- **Cover hot read paths with `INCLUDE`, only with columns that rarely change**: comparables' prices went from 334 buffers to 5 with `Heap Fetches: 0`; after the crawler touched 20 % of rows with vacuum held off, 409 heap fetches made it worse than a plain index scan. Read `Heap Fetches` in every index-only plan. [P-6]
- **Keep predicates sargable**: `first_seen_at::date = '…'` read the whole index (66 ms), the half-open range 7 buffers (0.14 ms); move arithmetic to the constant; convert Jalali dates to UTC instants in TypeScript, not in SQL on the column. An expression index must match the query's expression exactly. (Winand) [P-7]
- **Choose the index type by the operator**: B-tree for scalars and order; GIN for `jsonb @>`, arrays, `tsvector` and trigrams; GiST for ranges, exclusion constraints and geometry; BRIN for huge append-only time columns whose `pg_stats.correlation` is near 1 (24 kB against a 48 MB B-tree for the same one-week query); hash only for equality on long values, and never as a constraint. (PostgreSQL manual, Haki Benita, Lukas Fittl) [P-8, H-20]
- **A unique constraint is the natural key's index**: `listing_source_key_unique` is both the upsert arbiter and the lookup; never add a plain index beside it. [P-10]
- **Count the write bill: never index what the crawler rewrites on every pass.** With `last_seen_at` unindexed and `fillfactor = 90`, 67 to 74 % of crawl updates were HOT (17 MB of WAL); an index on it made them 0 % HOT (49 MB, three times slower). `listing` is created with `fillfactor = 90`; watch `n_tup_hot_upd / n_tup_upd`. **Measure** (Laurenz Albe, Winand) [P-11, H-8]
- **Retire unused and duplicate indexes carefully**: `pnpm db:unused-indexes` after a window that covers a full cycle; never drop what backs a constraint or serves a foreign key (they show zero scans until the day a parent is deleted); `EXPLAIN ANALYZE` itself increments the counters; a person agrees before a drop, which is `DROP INDEX CONCURRENTLY` in its own migration. Try a plan without an index locally with `BEGIN; DROP INDEX …; EXPLAIN …; ROLLBACK;` (holds an ACCESS EXCLUSIVE lock; development only). (Laurenz Albe, PostgreSQL wiki, Haki Benita, PlanetScale) [P-12, H-8, H-22]
- **Keep the planner's statistics honest**: `ANALYZE` after a bulk load; raise a skewed column's statistics target; `CREATE STATISTICS listing_make_model_stats (dependencies, ndistinct, mcv) ON make_id, model_id FROM listing` turned an estimate of 646 rows into 7,783 for an actual 8,182. Correlated ranges (old cars, high mileage) stay misestimated whatever you do. (PostgreSQL manual, Christofides) [P-14, H-12]
- **Enforce uniqueness of long URLs through a compact key**, `url_md5 uuid GENERATED ALWAYS AS (md5(url)::uuid) STORED` under a named UNIQUE (works as an `ON CONFLICT` arbiter); `sha256(convert_to(…))` is refused in a generated column because `convert_to` is STABLE (our `jsonb_sha256` wrapper is declared IMMUTABLE only because the database is UTF8). Measure sizes on real URLs first. (Haki Benita) [H-16]

## Measuring performance

- **`pg_stat_statements` and I/O timing are on from day one** (`db/postgresql.conf`); rank by **total** time, not by the slowest statement. `pnpm db:top-queries` prints total, share, calls, mean, rows and buffers per call and temp blocks. In the lab one count query was 59.9 % of all database time, and an N+1 loop showed only by its 21,020 calls. Failed and timed-out statements and network time are not in it. **Measure** (PostgreSQL manual, Samokhvalov, Kerstiens, Atkinson) [P-15, H-11]
- **Read `EXPLAIN (ANALYZE, BUFFERS)` for pages, estimates and loops**, twice (cold, then warm), bottom-up: estimated against actual rows (a factor of ten explains most bad plans); `loops` (times and rows are per loop); `Rows Removed by Filter` against rows returned; buffers per returned row; `Heap Fetches`; `Sort Method: external merge Disk`; `Trigger for constraint … time=` lines; `SERIALIZE` for wide rows (a `SELECT *` on embeddings showed 2.6 ms without it and 29 ms with it). Timing moves with the cache, block counts do not. Data-changing statements go inside `BEGIN … ROLLBACK`. **Measure** (Laurenz Albe, Samokhvalov, depesz, Christofides) [P-16, H-9]
- **Slow statements log themselves**: `log_min_duration_statement = 250ms`, `auto_explain` from 500 ms with buffers and without per-node timing, lock waits, every spill to disk, slow autovacuum (all in `db/postgresql.conf`; the worker role gets its own threshold). [P-17]
- **Measure on production-shaped data**: a seeded generator with realistic skew (a few models dominate, Tehran holds about 40 %), `ANALYZE`d, driven by the real mix of queries; report cold and warm runs and buffers, never one timing. A 100-row table makes a sequential scan the right answer. Performance claims never come from fixtures. **Measure** (PostgreSQL manual: "Always run ANALYZE first", Christofides) [P-19, H-10]
- **Review the SQL, not the builder code**: every new or changed query ships with the SQL it sends and its plan (before and after for a change), as GitLab's database review asks. [H-23, P-46]
- **Tools**: HypoPG (hypothetical indexes) and Dexter only on a development image; explain.dalibo.com or explain.depesz.com for long plans, never with real sellers' data; foreign SaaS monitors are unavailable from Iran until checked. [P-18]

## Query patterns

- **Keyset pagination, never deep `OFFSET`**: `WHERE (deal_score, id) < ($1, $2) ORDER BY deal_score DESC, id DESC LIMIT 20` took 0.06 ms at any depth, `OFFSET 59980` 66 ms and 60,227 buffers. A unique tiebreaker in the sort, the comparison and the index; one direction for all sort columns; «نمایش بیشتر» rather than page numbers. **The cursor must be exact in the column's type**: a `real` cursor passed as a literal compared as `double precision` and repeated a row on every page, and a `timestamptz` cursor that passes through a JavaScript `Date` loses its microseconds. Prefer integer sort keys (a deal score in basis points); for time keys carry the database's own text (`cast(listed_at as text)`) and cast it back. [lab 2026-09-27: a Date cursor returned an empty second page over rows a microsecond apart; the text cursor returned all three] (Winand) [P-20, search §3.4]
- **Counts: exact only below a cap, «بیش از ۱۰۰۰ آگهی» above it, estimates where a rounded number is honest.** A naive count of Tehran's active listings took 50 ms; a capped count `SELECT count(*) FROM (SELECT 1 … LIMIT 1001)` 0.57 ms; the planner's estimate cost nothing and was 3 % off for structured filters (useless for text queries). (Laurenz Albe, PostgreSQL wiki, GitLab) [P-21, search §3.5]
- **One round trip per page, never N+1**: a page's related rows come from `= ANY($1)` with one array parameter or one `JOIN LATERAL`; the lab went from 21 statements and 11.5 ms (59.6 ms with a 1 ms network each way) to 1 statement and 1.1 ms (3.6 ms). `IN ($1, $2, …)` changes the statement text with every page size. [P-22]
- **Select only the columns the screen needs**; list pages never read `payload`, `description` or an embedding. [P-23]
- **Write `OR` and multi-select filters so the planner can index them**: `model_id = ANY($1)` for chips; generate SQL with only the filters present, never `($1 IS NULL OR model_id = $1)` catch-alls; `UNION ALL` of two indexed queries for a real OR across columns. [P-24]
- **CTEs are inlined since PostgreSQL 12**: write them for readability; `MATERIALIZED` only when a subresult must be computed once (a relaxed vector scan re-sorted by exact distance). [P-25]
- **Prepared statements can switch to a generic plan after five runs.** node-postgres sends unnamed statements unless given a `name`, so each is planned with its values; that is why partial-index predicates must be literals and user values parameters. If a hot, skewed query goes generic, set `plan_cache_mode = force_custom_plan` for that role. [P-26, access-layer]
- **Parameterize every value; allowlist every identifier**: a sort from the URL maps through `{ price: 'asking_price_toman', newest: 'listed_at' } as const` with a default; PL/pgSQL dynamic SQL uses `format('%I')` and `USING`. Lint rejects SQL built by concatenation or interpolation and `sql.raw`. (node-postgres, PostgreSQL manual) [C-59]
- **Make the database do set work**: filter, join, aggregate and rank in SQL, never by loading a table into JavaScript. [P-46]

## Connections and configuration

- **Size a pool by cores, not users**: on 2 CPUs throughput peaked at 2 to 4 busy connections (about 2,400 to 2,800 transactions per second) and latency grew with every client after that (29 ms at 64). The web pool is `max: 5`, the worker's 3 to 5, and `max_connections = 50`. Measure `pool.waitingCount` before raising `max`: a starved pool usually means slow queries. (PostgreSQL wiki, node-postgres) [P-29]
- **One pool per process, created on first use and cached on `globalThis`** (`database.ts`), so hot reloading does not open a pool per edit; the worker gets its own module and `application_name`, and closes its pool on `SIGTERM`. An idle client's error is handled, or it crashes the process. [P-30]
- **PgBouncer only when processes outgrow one pool**, then in transaction mode: no session `SET` (use `SET LOCAL` or `set_config(…, true)`), no `LISTEN` (pg-boss notify needs a direct connection), no session advisory locks, prepared statements only with `max_prepared_statements`. [P-31]
- **Timeouts and `application_name` per role, never globally** (`db/bootstrap/10-roles.sql`): web `statement_timeout 5s`, `lock_timeout 2s`, `idle_in_transaction_session_timeout 10s`, `transaction_timeout 15s`; read-only sessions and 30 s for `carshenas_readonly`; `lock_timeout 5s` for migrations; the worker's longer limits arrive with it. A known long job raises its limit inside its own transaction with `set_config('statement_timeout', …, true)`. Alert on 57014 and 25P03. (PostgreSQL manual: "Setting statement_timeout in postgresql.conf is not recommended because it would affect all sessions", Kerstiens) [C-45, P-27]
- **Autovacuum per table for churn**: `listing` vacuums and analyzes after 2 % of rows change (default 20 %); insert-only history gets a low `autovacuum_vacuum_insert_scale_factor` so index-only scans stay possible; never disable autovacuum on a table. (Laurenz Albe) [P-33]
- **The Docker service** pins `pgvector/pgvector:0.8.6-pg18`, gives `/dev/shm` 1 GB (a parallel HNSW build failed on the default 64 MB), mounts `db/postgresql.conf`, publishes on 127.0.0.1 only, and limits memory and CPUs to the VPS the settings describe. [P-34]

### Configuration

`db/postgresql.conf` holds the 4 GB column. Start from these values, then tune by measurement (`SHOW` after a restart); CS-23 re-derives them for the real VPS. PostgreSQL shares the box with the app and the worker, so `effective_cache_size` sits at the conservative end. (PostgreSQL manual, PostgreSQL wiki, Crunchy Data, pgvector README) [P-32]

## Testing

- **Test against real PostgreSQL of the production major, never a mock.** Two layers here: the schema tests in `pnpm check` run PGlite (PostgreSQL 18.3 in WebAssembly, one connection, about two seconds to migrate) inside rolled-back transactions; the `*.db.test.ts` integration tests run in `pnpm db:check` against the Docker server on a freshly migrated scratch database of their own (`carshenas_<pid>_check`), and a test that writes refuses any database whose name does not end in `_check` or `_test`. (IntegreSQL, Peter Downs) [C-53]
- **When tests need commits, retries, deferred constraints or concurrency, give each worker its own database cloned from a migrated template** (`CREATE DATABASE … TEMPLATE`, about 36 ms per clone); rolling back hides deferred foreign keys, freezes `now()` and cannot run code that commits. In a rolled-back test, `SET CONSTRAINTS ALL IMMEDIATE` before asserting. (Peter Downs, IntegreSQL) [C-54, C-29]
- **Test the database's own rules by SQLSTATE and constraint name**, one failing write per named constraint and per trigger (`schema-constraints.test.ts`); for row-level security later, an allowed write proves itself by its `RETURNING`, a denied one by zero rows and an unchanged read. (pgTAP, Supabase) [C-55]
- **Test concurrency on purpose**: two connections, a barrier (a row lock or an advisory lock held by one), assertions on the end state (one row, one 40001). The lab scripts in the appendix are the seed. (Kleppmann) [C-56]
- **Migrations run from empty to head, back down and up again on every check** (`pnpm db:check`), with the schema dump and the types compared; before a risky deploy, against a production-sized copy with the production timeouts. (Samokhvalov) [C-57, H-4]
- **Factories insert through the application's own functions with realistic Persian values**, including the zero-width non-joiner and both digit scripts, and unique natural keys per test. [C-54]

## Security and privacy

- **Separate roles; the app never connects as the owner or a superuser** (`db/bootstrap/10-roles.sql`): `carshenas_owner` owns every object and cannot log in; `carshenas_migrate` logs in and becomes the owner for migrations; `carshenas_web` gets SELECT on what pages show and DML only on what people own, table by table; `carshenas_readonly` has read-only sessions and SELECT on everything through default privileges; `carshenas_worker` arrives with CS-6. Ownership carries the right to alter and drop, and owners bypass row-level security. A leaked web credential must not read snapshots or phone hashes. (PostgreSQL manual) [C-58]
- **Agents inspect through the read-only role and never rely on a tool's read-only mode**: two MCP servers' read-only modes were escaped (stacked statements; a function in FROM). The agent's experiments run on its local container only; the guard hook refuses `DROP`, `TRUNCATE`, `docker compose down -v` and `dbmate drop`, which the person runs themselves. No database MCP server. (Datadog Security Labs, Claude Code's MCP docs) [H-26]
- **Phone numbers are stored only as HMAC-SHA-256** of the normalised number, keyed by a secret that never enters the database, with a `key_version` for rotation (owner; ADR-0008 point 7). A per-row salt would make the same number differ on Bama and Karnameh and defeat duplicate detection; an unkeyed hash of a 10^9-number space is reversed by enumeration. Only the worker reads the hashes; never expose them through a page or an API. (Moxie Marlinspike, AEPD and EDPS) [C-61, data-model]
- **Personal data stays out of snapshots, logs, cache keys and tags**: phone numbers are removed before a payload is stored; the server logs statements without their bind parameters (`log_parameter_max_length = 0`, `auto_explain.log_parameter_max_length = 0`) and errors without their DETAIL, which prints the failing row (`log_error_verbosity = terse`); plans that `auto_explain` logs still show the constants a query was planned with, so production decides whether to keep it (CS-23); SQL is logged with parameters only in development, on the app side (`CARSHENAS_LOG_SQL=1`); `'use cache'` keys and tags are plain text. [ADR-0008 point 7, CS-4 review]
- **Only the migration role may create temporary tables** (`db/bootstrap/create-database.psql`): a temporary table is searched before `public` for an unqualified name, so a role with TEMPORARY could stand one in for `listing_status_transition` inside the lifecycle trigger. Trigger and helper functions also qualify the tables they read and pin `SET search_path = public, pg_temp`. [CS-4 review, C-58]
- **Row-level security will be the second lock on native sellers' rows**, never the only one: policies name the role (`TO carshenas_web`), read the seller from `set_config('app.seller_id', $1, true)` inside the request's transaction, and views over those tables use `security_invoker`. Crawled listings are public and need none. (PostgreSQL manual, Supabase) [C-60]
- **SECURITY DEFINER functions pin `search_path`** (trusted schemas, `pg_temp` last) and revoke EXECUTE from PUBLIC; the catalog test fails one without a `search_path`. [C-58]
- **Secrets live in `.env`** (local) and the server's environment; connection strings per role come from `example.env`'s shape; `src/server/env.ts` is the only reader. [AGENTS.md]

## Conventions the tests enforce

`apps/web/src/server/db/schema-catalog.test.ts` reads the catalog of a database migrated from `db/migrations` (in PGlite, inside `pnpm check`); `schema_migrations` is dbmate's and exempt. A failure lists the table, column or constraint to fix.

- Every table has a primary key and a `COMMENT`.
- No column is `timestamp`, `timetz`, `char(n)`, `varchar`, `money` or `json`.
- Primary and foreign key columns are `bigint`, `text` or `uuid`; a single-column `bigint` primary key is `GENERATED ALWAYS AS IDENTITY`; no default draws from a sequence (`serial`).
- Constraints start with `<table>_` and stay under 63 bytes: primary keys are exactly `<table>_pkey`, foreign keys end in `_fk`, unique constraints in `_unique`, exclusion constraints in `_excl`, and no CHECK ends in `_check` (PostgreSQL's automatic suffix). Indexes that back no constraint start with `<table>_` and stay under 63 bytes; unique ones end in `_unique`, the others in `_idx`.
- Every foreign key has a non-partial index whose leading columns are exactly its columns, or a `COMMENT ON CONSTRAINT` starting `unindexed:`.
- No invalid index, no unvalidated (`NOT VALID`) constraint left behind, no two identical indexes, no SECURITY DEFINER function without a `search_path`.
- Every single-column CHECK of the form `col IN (…)` has an override in `apps/web/.kysely-codegenrc.json` with exactly those values, `| null` exactly when the column is nullable, and `Generated<…>` exactly when it has a default.
- Every identity or stored generated column is overridden as `ColumnType<T, never, never>` there, so code can never insert or update it.
- No check passes vacuously: the last test creates, inside a rolled-back transaction, tables, indexes, constraints and a function that break every rule clause by clause, and fails unless each check reports each planted name.

`schema-constraints.test.ts` proves the rules by what PostgreSQL rejects, each with its SQLSTATE and constraint name: the crawl-interval floor (a missing interval included), an official-API source never crawled, a stopped source recording when and why, source codes and origins, policy-check conditions, append-only policy checks, fetches and snapshots (23000 with the trigger's name), the purge, one listing per source key and the upsert on it (including a re-crawl straight to `sold`), external-only listings and the origin foreign key, market dates and the required sighting, the status lifecycle (a temporary table cannot widen it), one running crawl per source citing its own source's policy, a fetch pointing only at its own source's listing and that listing's snapshot, one snapshot per distinct content, and the privileges of the web and read-only roles. `database-errors.db.test.ts` proves the same mapping through node-postgres and Kysely (NOT NULL by column), and `database-server.db.test.ts` that the web role cannot create temporary tables and that the server compresses with lz4 and logs no bind parameters.

## Resolved disagreements

- **Index every foreign key?** GitLab, Supabase and PlanetScale say always; Laurenz Albe says not when the referencing table is small, nor when no join needs it and parents are never deleted. The owner chose "always, exceptions named" (decision 7), so the exception is visible in the migration and checked by the catalog test. [H-7, P-9]
- **Insert and catch, or check first?** Neither as usually written: `ON CONFLICT` for batch writes (no dead tuples, no aborted transaction), insert-and-map for single writes a person triggers, a read first only as a courtesy for the form, never as the guard. [C-31, C-34, H-1]
- **Constraint names**: GitLab uses prefixes (`check_…`, `fk_…`), PostgreSQL's automatic names use `_check`, `_fkey`, `_key`. We use suffixes that differ from the automatic ones, so a forgotten name is caught. [H-6, C-22]
- **Plural or singular tables**: the integrity pass wrote plurals; the data-model pass and the migrations use singular nouns, which is the rule. [C-22, data-model]
- **Integer or `bigint` keys**: Andrew Atkinson uses `integer` for small databases; Laurenz Albe, Samokhvalov and GitLab's conversion procedure argue for `bigint` from the start; the owner chose `bigint` (decision 9). UUIDv7 everywhere (Christofides) loses to twice the size and a leaked creation time. [C-4, C-5, H-25]
- **Money as `numeric`** (Supabase, pg-aiguide, Christensen) fits currencies with fractions; toman and rial amounts are whole numbers, so `bigint` is exact and faster, and the owner chose integers. [C-9]
- **Idempotent DDL** (`IF NOT EXISTS`, Supabase's DO blocks, Squawk's `prefer-robust-stmts`) assumes re-running a half-applied file; dbmate wraps each file in a transaction, so versioned migrations fail loudly instead. [H-4]
- **Reversible migrations** (GitLab: "must be reversible") against forward-only practice: every down section must work in development and in `pnpm db:check`; production fixes forward. [C-52]
- **Timeouts database-wide** (Kerstiens) or **per role**: per role, so the web role is strict and migrations are not cut off. [C-45]
- **Few indexes or composites**: the PostgreSQL manual says multicolumn indexes "should be used sparingly"; Lukas Fittl's benchmark and our labs favour one composite per measured query family. Few indexes, each composite and measured. [P-3]
- **Tests in PGlite or in Docker**: PGlite in `pnpm check` for speed (same major, one connection); the Docker server in `pnpm db:check` for the pool, the driver, concurrency and the migration replay. [C-53, C-54, harness: Mechanical checks]
- **Vectors in a separate database** (Crunchy Data, for index-build load) or **the same one** (pgvector, Supabase): the same database (decision 8), with HNSW builds in quiet hours. [H-18, P-38]
- **HNSW by default** (the vendored pg-aiguide guide) or **exact first**: exact search inside a B-tree-filtered block measured recall 1.00 in 5 ms; HNSW only when a query needs whole-table similarity or an exact scan passes about 100 ms (decision 8). [P-35]
- **Photos by embedding or by perceptual hash**: a 64-bit pHash with an exact Hamming search found 100 of 100 near-copies, faster and smaller than pgvector's HNSW on `bit(64)` (decision 8); embeddings match two different white Prides. [P-45]
- **Crawl policy in the database or in the crawler**: row-local rules are constraints now; the cross-row backstops (latest policy check, stop on block) are triggers that arrive with the crawler in CS-6. [data-model]
- **Soft deletion**: a status with a time for business states, hard deletes through a purge for removal requests. The UI's undo for deleting a saved search is a short pending state or a re-insert, not a global `deleted_at`. [C-20, H-24]
- **MERGE or ON CONFLICT**: MERGE only for one writer synchronising a set; it is not a concurrency-safe upsert. [C-35]
- **Domains**: the PostgreSQL manual presents them for shared rules, Squawk discourages constrained domains; use them only when creating the tables. [C-11]
- **Row-level security as authorization**: never alone; the app authorises in the data layer, RLS is the second lock. [C-60]
