# ADR-0028: Serve search from a table of searchable listings that the worker keeps fresh by marking changed listings, with keyset pages and counted facets

- Status: accepted by delegation (2026-10-01; the owner asked that lane decisions be taken without him, "decide yourself based on best you recommend"); revised on 2026-10-02 after the database and task reviews, before it reached main
- Date: 2026-10-01
- Deciders: Pedrum (delegated to the CS-59 lane); the coordinator, under the same delegation, for the two scope points below
- Related: CS-59, CS-61, CS-62, CS-63, CS-70, CS-72; ADR-0011, ADR-0017, ADR-0027; `docs/design/data-model.md` ("Added by CS-59"); the database skill's `references/search.md`; `docs/evidence/search-api/2026-10-02/`

## Context

CS-58 defined every filter over the view `listing_filter_row`, which computes a listing's row from six tables, the latest valuation run and the current extraction on every read (2 to 55 ms per catalogue on 23,364 listings, about 0.9 s once most are extracted; the filter options are a full scan). Pages need results in the order a buyer chose, the next page without OFFSET, a total and facet counts, Persian words typed in any script, and only listings that can be shown. The rows change all day: crawls, derivations, the catalogue's matching, extractions and the nightly valuation run.

Who decided the scope. ADR-0017 (the owner, 2026-09-28) decided that a results page shows only listings seen within 48 hours (point 6) and that details are read only for tracked models, new or changed listings and pages a buyer opens (point 3). The coordinator decided on 2026-10-01 that the table has one row per listing, not per vehicle (ADR-0027, data-model question 6). The coordinator decided on 2026-10-02, after the database review, that a listing is searchable when its details have been read (`price_type` is set), which replaces the first version of this ADR, where this lane chose "a tracked model" from ADR-0017's wording: the tracked list lives in code, an empty list deleted every row, and details are only read for tracked models and pasted links anyway. A list row alone has no title, price, year, mileage, city or photo, cannot be a card or be rated, and on 2026-10-02 was three quarters of the active listings; it enters by itself when its details are read.

## Decision

Search reads `search_document`, one row per searchable listing, with the view's columns under the same names, so CS-58's predicates run on it unchanged. Searchable means active, from a public source, details read and seen within 48 hours.

**Keeping it fresh.** Statement-level triggers on `listing`, `listing_photo`, `extraction_field` and `valuation_run` append a mark to `search_document_stale` (an append-only queue with no unique key and no foreign key, so an insert never waits: a crawl or a derivation is never held up by a build). `search.refresh` every minute takes up to 2,000 marks, rebuilds those rows, and commits rows and marks together; then, in transactions of their own, it expires rows past 48 hours, recounts `search_facet_count` (the searchable total, the listings seen, each catalogue, each option of the row-backed filters: written only where a count changed) and rebuilds the vocabulary when `search_build_event` says it was built before the rows last changed. `search.rebuild` runs at 04:37, at the worker's start when the table is empty or the last full rebuild is over 26 hours old, and by `pnpm search:rebuild`: every row in id ranges of about 2,000 listings, in one transaction with its own limits, then the counts, the vocabulary and the statistics, and last the time of the full rebuild. Two builds never interleave: the refresh `pg_try_advisory_xact_lock`s and skips its tick when a build holds it; the rebuild polls for up to 30 seconds.

**Words.** One immutable normaliser (`search_normalize`) for documents and queries, our own configuration `fa_search`, a generated `tsvector` over the stored text (title, catalogue names and aliases, year, city, district, colour, body type), and `search_query`: every word required, a prefix except numbers; a word no listing has is replaced only by the exact word of a common listing-wide vocabulary that is one edit away (letters only, four or more, two edits from seven letters, in at least half a percent of the listings and ten, at most three tried), and the corrections and the words that match nothing come back so a page can say so.

**The API.** `features/search/server/search-queries.ts` for Server Components (`searchListings`, `readSearchFacets`, `readFilterOptionCounts`, `readCatalogueCounts`, `readSearchCoverage`) and `GET /api/search` with the page's own URL parameters plus `cursor`, `limit` (0 to 48; 0 is only the count) and `facets=1`; both return DTOs. A page continues by an opaque keyset cursor (the order, the last row's key as text checked against each column's type, and the first page's total, so a later page counts nothing). A keyset page is the union of branches, each one range of the order's index (`searchAfterBranches`), with row comparisons for the tail; every read composes the filters, the freshness window and the words in one function (`searchableWhere`), which CS-72's matcher shares. Totals come from the counts for everything and for a catalogue as it is, and are counted live up to 1,000 («بیش از ۱٬۰۰۰») otherwise; the facets of a filtered search are counted live, each without its own filter, sharing one scan among the facets whose filter is not in the search.

**Indexes.** One B-tree per order, a city composite, a GIN, and nine single-column indexes on columns with rare values. Fill factor 80 and no index on `last_seen_at`.

## Alternatives considered

- **Tracked models as the table's scope** (the first version): a code list inside a derived table; replaced by the details condition (above).
- **Refresh after each writer**: no triggers, but every future writer must remember it. **A materialized view with REFRESH CONCURRENTLY**: recomputes every row each time. **A shadow table swapped by rename**: the worker does not own the table, and 25,000 rows need no swap.
- **A unique key on the marks** (`ON CONFLICT DO NOTHING`, the first version): a writer whose trigger met a mark a refresh was deleting waited for the refresh. Append-only marks never conflict.
- **One transaction for the whole refresh**, counts and vocabulary included (the first version): it held its marks through the recount, the vocabulary and the statistics, and failed on the worker role's five-second lock timeout when two builds met at 04:30.
- **A btree on `last_seen_at` for an indexed expiry**: 0.35 ms against 15.9 ms at 25,000 rows, but it makes every sighting a non-HOT update (0 % against 26 to 56 % at fill factor 80). Revisit at about 80,000 rows.
- **Composite indexes for models and makes** (the review's proposal): measured unused while every searchable model had 1,200 or more listings; a single-column index serves a rare one.
- **A `ts_rewrite` alias table** (the research's design): the catalogue's names and aliases in each document matched every Latin-typed model name without it.
- **OFFSET pages and exact counts everywhere**: OFFSET degrades with depth, and counting every match of a broad search cost 6 to 16 ms against a 0.9 ms page.

## Consequences

- Positive (24,996 and 99,989 synthetic listings; the lane's 3,008; `docs/evidence/search-api/2026-10-02/`): a first page of every order 0.1 to 0.5 ms and 27 to 46 buffers; a keyset page at any depth 0.08 to 0.8 ms and under 56 buffers; a filter on a rare value 0.1 to 2.7 ms (8 to 23 ms and up to 8,960 buffers before the indexes); a catalogue 0.1 to 3 ms; the lane's slowest query 5.8 ms. The API's p95 was 52 ms with one client and 160 ms with eight on the lane, 82 and 206 ms on 25,000 listings. A stored search, the URL and the API run the same SQL.
- Negative / risks: a change reaches search within about a minute; popularity ranks and catalogue names refresh with the nightly rebuild. **Facets of a broad filter cost about 2 µs a matching row** (38 to 45 ms at 25,000 listings, 75 to 194 ms at 100,000), so at 100,000 listings the API's p95 is 316 ms with one client and 554 ms with eight: past about 30,000 matching rows, cache the facets per search (no words in the key) or sample them. A from-empty fill takes 15 s for 25,000 listings and 76 s for 100,000, inside a transaction limit the rebuild sets (600 s); the refresh's batches are short. The tables and the 48-hour window mean a copy whose crawler is paused empties in two days. A new table the search row reads needs its own trigger.
- Follow-ups: CS-61 and CS-63 consume the API (`readSearchCoverage` for a line on how much is searchable, `text` for «نتایج برای …»); CS-72 matches search files with `searchableWhere` as the worker; CS-62 uses `search_query`'s words and a labelled set to measure typo and alias recall (the research's trigger 6); an alias for «پزو» (three letters, never corrected) belongs to the catalogue; the facets' cache at the scale above.
