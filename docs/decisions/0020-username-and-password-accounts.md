# ADR-0020: Accounts are a username and a password, checked by our own code, with sessions in PostgreSQL and a superadmin that only a command can make

- Status: accepted on 2026-09-29 by the owner, who chose, among the options put to them: "8 characters" for a buyer's password (against 15 and 12), "No recovery for now" (against a recovery code at sign-up), "Latin, digits and _" for usernames (against Persian letters too) and "12 hours" for a superadmin's session (against 12 hours with 1 hour idle, and 30 days like buyers)
- Date: 2026-09-29
- Deciders: Pedrum

## Context

The owner's product plan of 2026-09-29 needs accounts: a buyer signs up to hand a search to Karshenas, mark listings and receive notifications, and the superadmin section needs a real sign-in. ADR-0003 deferred authentication to the first feature that depends on who the visitor is; this is it. On 2026-09-29 the owner decided that, for now, an account is a username and a password only (no email, no phone number, no one-time code), that the first superadmin, `pedram`, is created in the database with a strong password, and that a superadmin lands on the admin dashboard after signing in. PostgreSQL is the only data service (no Redis), nothing may depend on a service that is sanctioned or unreachable from Iran (which had an 88-day shutdown of international traffic in 2026), messages are Farsi and come from named constraints, and no personal data reaches the logs.

## Decision

1. **Our own code, no auth library or service.** `packages/accounts` holds what the web app and the command share (password rules and hashing, username rules); `apps/web/src/server/auth/` holds sessions, the current account, role guards, throttling and the same-origin check.
2. **Usernames**: 3 to 30 characters of `a`–`z`, `0`–`9` and `_`, starting with a letter (Telegram's alphabet). Typed capitals become lowercase and Persian or Arabic-Indic digits become Latin before the check; the database stores the lowercase form under a format CHECK and `account_username_unique`, whose violation reads «این نام کاربری گرفته شده است. نام دیگری انتخاب کنید یا وارد شوید.», true whether someone else holds the name or the person does. Names such as `admin`, `root`, `support`, `carshenas` and `karshenas` are refused at sign-up with the same message. While a name is typed, a rate-limited Route Handler says whether it is free; the insert still decides. A username is not a secret, but it is never shown to other buyers and never logged, because people sometimes type their password into it.
3. **Passwords**: 8 to 128 characters, counted as code points; no composition rules, expiry, hints or security questions; paste and password managers allowed, with a show-password button. Before the checks and the hash, a password is normalised to NFC, non-ASCII spaces become a space, Persian and Arabic-Indic digits become Latin and Arabic ي and ك become Persian ی and ک, so the same password works from a phone and from a Windows keyboard (a named departure from ASVS 6.2.8, "exactly as received"). It is refused, with the reason in Farsi, when it is one of the 100,000 most common passwords (the NCSC list, exact match, also after lowercasing and after mapping keys typed with the Persian layout back to Latin), or the username, the site's name or a variant of either. Nothing is checked against a service abroad.
4. **Hashing**: Argon2id with OWASP's parameters (19 MiB, 2 passes, 1 lane), a 16-byte salt and a 32-byte tag, stored as a PHC string in `account.password_hash` (a CHECK on its `$argon2id$v=19$` prefix). The `argon2` package (the reference C implementation, prebuilt) runs it on Node.js 22; when the project moves to Node.js 24, Node's own `crypto.argon2` replaces it with the same strings. At most two hashes run at once per process; a sign-in rehashes when the stored parameters are older than the current ones; an unknown username is verified against a dummy hash so it takes the same time. No pepper yet: it can be added later by rehashing at sign-in.
5. **Sessions**: a random 32-byte token; the database keeps only its SHA-256 (`account_session.token_sha256`, UNIQUE). Every sign-in makes a new token; the role is read from `account` on every request, never copied into the session. A buyer's session lasts 30 days from sign-in and is not extended; a superadmin's lasts 12 hours. Sign-out deletes the row and the cookie; a password set through the command deletes the account's sessions; a database CHECK bounds every session's lifetime.
6. **Cookie**: `__Host-session`, `Secure; HttpOnly; SameSite=Lax; Path=/`, with `Max-Age` ending with the session. Over plain http on a loopback host (development and the browser tests) it is `session` without `Secure`, because Playwright's WebKit refuses every `Secure` cookie over http. The choice follows the request's scheme and host, never `NODE_ENV`.
7. **Cross-site requests**: state changes only through Server Actions, which are POST requests. Besides Next.js's own origin check, every action starts with ours: `Sec-Fetch-Site` must be `same-origin`, or, without it, `Origin` must match the host; a request with neither is refused. `SameSite=Lax` is written out.
8. **Throttling in PostgreSQL** (`auth_throttle`, keyed by HMAC-SHA-256 of the typed username, a device token or the client address under a server key, so no username or address is stored):
   - per account name: five free failures, then waits from 30 seconds doubling to one hour; a success clears it; attempts on one name never run in parallel;
   - per browser that signed into that account before (a signed device cookie): its own counter, so nobody can lock the owner out by guessing at `pedram`;
   - per client address (the rightmost `X-Forwarded-For` entry, written by our one reverse proxy): 100 failed sign-ins and 20 sign-ups an hour, generous because Iranian mobile operators share addresses; both limits are settings.
   One Farsi message for a wrong username or password, whichever it was; a throttled answer says when to try again.
9. **Roles**: `account.role` is `buyer` (the default) or `superadmin`. The web database role may insert only `username` and `password_hash` and update only `password_hash` (column privileges), so no bug in the product can grant a role. A superadmin is created or promoted only by `pnpm account:superadmin <username>`, run as `carshenas_migrate`, which generates a 24-character password and prints it once, or reads one from standard input, never from an argument or the environment; every role change is appended to `account_role_change`.
10. **Authorisation next to the data**: `requireAccount()` and `requireSuperadmin()` in `src/server/auth/` are called by every protected page, Server Action and query; a layout or `proxy.ts` is never the guard. Everyone but a superadmin gets a 404 from admin pages, which carry `noindex` and are linked only from the signed-in superadmin's own account menu, never from what visitors and buyers see. After signing in, a superadmin goes to the admin dashboard, or to `next` when it points inside the admin section; a buyer goes to `next` when it is a path on this site outside the admin section, otherwise to the home page.
11. **Recovery**: none until phone sign-in arrives; the sign-up page says so, and the sign-in page offers no recovery link that cannot work.
12. **Logs**: one line per sign-up or sign-in attempt with its outcome, the account id when known and the throttle that answered; never the typed username, the password, a token or an address.
13. **Later**: a phone number with a one-time code arrives with its own task, which chooses the SMS provider reachable from Iran and its fallback, and brings recovery with it.

## Alternatives considered

- **Better Auth 1.7**: requires an email for every account until its v2, checks usernames by reading before inserting, stores session tokens in plain text, and skips its rate limiter and origin check for calls from Server Actions, which is every call here.
- **Auth.js v5**: password sign-in gets no database sessions (JWT only), so sessions cannot be ended on the server.
- **iron-session**: encrypted cookies that cannot be revoked.
- **An identity server** (Keycloak, Ory Kratos, Zitadel): a second service with its own schema and screens on a 4 GB server.
- **SaaS** (Clerk, Auth0, Supabase Auth, WorkOS): their terms exclude Iran, and Auth0 blocks it.
- **A 15-character minimum** (NIST SP 800-63B-4's rule for password-only accounts): the strongest reading, but more friction and more forgotten passwords while nothing can be recovered.
- **Locking an account after N failures**: lets anyone lock the owner out; growing waits with a device exemption slow guessing without that.
- **The superadmin from an environment variable** read at start-up: the web role would need the right to grant the role.

## Consequences

- Positive: no dependency abroad; the database refuses a role grant from the product and stores nothing that works as a password or a session; every rule has a test; phone sign-in can be added beside passwords without changing sessions or roles.
- Negative / risks: we own the review of security code; buyers who forget their password lose the account until phone sign-in exists; usernames can be checked for existence through sign-up (limited per address); named departures from NIST SP 800-63B-4 (15-character minimum, a disable after 100 failures, a token in every POST) and ASVS 6.2.8.
- Follow-ups: CS-40 builds the section on this sign-in; changing a password and signing out everywhere; a daily sweep of expired sessions and throttle rows; the e2e job needs PostgreSQL (CS-38); `CARSHENAS_AUTH_KEY` and the proxy's `Host` and `X-Forwarded-For` on the server (CS-37); Node.js 24 and Node's own Argon2.
