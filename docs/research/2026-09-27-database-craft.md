- Date: 2026-09-27

## Findings: short answers

### 1. Checks: invariants in the database, judgments in the application, messages in both

The database owns every rule one row, one key or one reference must satisfy, because it is the only layer every write passes through: the crawler, the extraction worker, Server Actions, a future seller app, a fix typed into `psql`, a migration's backfill [C-24]. The application repeats the checks a person can trip over, earlier and in Farsi beside the field, and turns the database's rejection into the same message by SQLSTATE and constraint name [C-25, H-6]. Rules that span rows or depend on the outside world (a seller's quota of free listings, a price that is implausible for the model, a crawl allowed only under the latest policy check) live in code inside a transaction that makes them safe: lock the parent row or run SERIALIZABLE and retry [C-39]; never a CHECK that calls a function or a plain trigger, which both race [C-30, H-13]. The split is not "simple checks in the database, complex ones in the app"; it is invariants in the database, judgments and cross-row policies in the app, messages in both.

### 2. Duplicates: declare the constraint, make the conflict part of the statement

Only a unique constraint is safe: two sessions that both checked first inserted the same Bama listing twice [C-31, integrity lab 2a]. Batch and crawler writes use `INSERT … ON CONFLICT … DO UPDATE … WHERE … IS DISTINCT FROM …`, which also skips no-op writes [C-33, H-1, H-2]. Plain insert-and-catch works for rare conflicts but costs more than it looks: the failed insert aborts the transaction (25P02) unless a savepoint wrapped it, and it leaves a dead tuple and burns an identity value (1,000 failed inserts grew the heap from 72 to 136 kB) [C-34]. Haki Benita states the useful rule of thumb: catching the violation suits rare duplicates, `ON CONFLICT` common ones [H-1]. `ON CONFLICT DO NOTHING … RETURNING` returns nothing for an existing row, so get-or-create re-selects in a new statement on PostgreSQL 18 [C-32]; `MERGE` is not a concurrency-safe upsert [C-35]. A read before the write is a courtesy to the person, never the guard.

### 3. Indexes: for a query, not a column, and priced

A senior engineer indexes a query when evidence says it matters: it ranks high in `pg_stat_statements` by total time, its plan reads far more buffers than it returns rows, or it is a structural certainty such as a foreign key that parent deletes and joins walk [P-1 to P-14]. The index follows the query: equality columns first, then the one range column or the `ORDER BY` columns in the same direction and NULLS order, a partial predicate for the rows actually searched (written as a literal in the query, since a bound parameter hides a partial index under a generic plan), `INCLUDE` for an index-only scan. It is proved with `EXPLAIN (ANALYZE, BUFFERS)` before and after, and priced: every index is paid on every insert and non-HOT update. In the lab the right column order read 5 index pages where the wrong one read 758; a partial index was 1.6 MB instead of 11 MB; a missing foreign-key index made deleting 20 listings take 4.5 s instead of 1.3 ms; one index on `last_seen_at` turned 70 % HOT updates into none and nearly tripled the write-ahead log per crawl pass [performance.md, question 3]. A week later, `pg_stat_user_indexes` shows what nobody scans [H-8].

### 4. Measurement: the workload, then the plan, then the logs

Three layers [P-15 to P-19, H-9 to H-11]. **Workload**: `pg_stat_statements` with `track_io_timing`, ranked by total time, then calls, then mean; in the lab one count query was 60 % of all database time, and an N+1 lookup was invisible by time but obvious by calls. **One query**: `EXPLAIN (ANALYZE, BUFFERS)` on production-shaped data, read for estimated against actual rows, `loops`, rows removed by filter, buffers per returned row, sorts that spill and trigger time; buffers are compared, not milliseconds. **Continuous**: `log_min_duration_statement` and `auto_explain` with timing off catch the slow plans nobody ran by hand. Benchmarks use `pgbench` scripts that imitate the real mix and a realistic network round trip (1 ms each way turned 21 statements from 11 ms into 60 ms). CS-4 turned these on from day one in `db/postgresql.conf`, with `pnpm db:top-queries` and `pnpm db:unused-indexes`.

### 5. Vectors: exact first, approximate only when a query needs it

Embeddings go in a narrow side table as `halfvec` (half the size and still stored inline; a `vector(512)` of 2 KB moves to TOAST, which made exact scans 4.9 times slower), with the model name and version on each row [P-36]. Duplicates share make, model and roughly the year, so a B-tree filter followed by an exact distance sort gives perfect recall in about 5 ms. HNSW (`halfvec_cosine_ops`, `m = 16`, `ef_construction = 64`) comes only when a user-facing query needs similarity across the whole table, with `hnsw.ef_search` set per query, `hnsw.iterative_scan = relaxed_order` for filtered queries, `maintenance_work_mem` at least the index size and a matching Docker `shm_size`, and recall measured on our own labelled data: on random vectors the same index returned 8 % of the true neighbours [P-35, P-37 to P-43, H-18, H-19]. Duplicate photos use a 64-bit perceptual hash in a `bigint` and an exact Hamming search: a sequential scan of 500,000 hashes took 44 ms, an exact B-tree multi-index search 0.8 ms, both finding 100 of 100 planted copies [P-45]. Pin pgvector 0.8.6: 0.8.3 and 0.8.4 fixed HNSW vacuum bugs, one of them possible index corruption.

### 6. Working with the database, and keeping Claude Code to it

The habits: read the actual SQL of every query, including what a builder generates, in server-only named functions, and explain it before review; make the database do set work (one query per screen region, keyset pagination instead of deep `OFFSET`, 66 ms against 0.06 ms at page 3,000); keep transactions short and never across an HTTP fetch or an LLM call; give every role its timeouts and `application_name`; hold one small pool per process sized by CPU cores (the 2-core lab server peaked at 2 to 4 busy connections, and 64 clients multiplied latency by 40); change the schema online; write down what was measured [P-20 to P-31, P-46, C-43, C-45, C-58].

Keeping an agent to them is a harness, built in CS-4 after pass E's recommendation:

- **Knowledge**: the `database` skill, whose `references/craft.md` carries these tips with their IDs; `.claude/rules/database.md`, which loads for migrations, `src/server/db` and feature `server/` files.
- **Mechanical checks**: Squawk on every migration's up section; ESLint rules that reject SQL built by concatenation or interpolation and keep the driver inside `src/server/db`, each proven by a lint self-test sample; schema tests in PGlite inside `pnpm check` that prove constraints by SQLSTATE and name and lint the catalog (primary keys, types, key types, names, foreign-key indexes, no invalid or duplicate index, union types in the codegen config); `pnpm db:check`, which replays every migration up, down and up on a scratch database and compares the schema dump and generated types.
- **Review and safety**: the read-only `database-reviewer` agent, which reviews with evidence it produces (replayed migrations, Squawk's report, each changed query's `EXPLAIN (ANALYZE, BUFFERS)`); a guard hook that refuses commands destroying database data or the volume, leaving them to the person; no MCP server, because the hosted ones call US services at run time, Postgres MCP Pro is unrestricted by default with a reported read-only bypass, and the read-only mode of Anthropic's archived reference server was escaped by SQL injection; agents use `pnpm db:psql` as the read-only role instead [H-26, harness.md sections 8 and 9].

### 7. Modeling lessons, as a database course teaches them

Stanford's CS145 notes build relational design on functional dependencies: "Functional dependency "A -> B" says a given A value always has the same B value." (Jennifer Widom, CS145 Lecture Notes 6, http://infolab.stanford.edu/~ullman/fcdb/jw-notes06/reldesign.html, spring 2006) [C-1]. The lessons, in order [C-1 to C-23]:

1. Write the dependencies down before drawing tables; decompose until each fact is stored once (BCNF), and keep a redundant column only when a constraint keeps it true, such as a composite foreign key that stops a trim from sitting under the wrong model [C-1, C-2].
2. Keys: a `bigint` identity for joins, the natural key as a named UNIQUE constraint, UUIDv7 only for ids minted outside the database; ids are neither counts nor secrets [C-4, C-5].
3. NULL means unknown, not zero or empty; NOT NULL by default, and know three-valued logic's traps [C-7].
4. Types carry rules: `text` with a CHECK, money as `bigint` in a named unit, `timestamptz` for instants and `date` only for Tehran days, one state column with a CHECK rather than a cluster of booleans, JSONB for payloads rather than for modeling, child tables rather than arrays you search [C-8 to C-15].
5. Time: immutable snapshots and append-only observations, "current" values derived from them, periods as ranges with a non-overlap constraint, a state with a time instead of a soft delete [C-16 to C-21].
6. Names and comments are documentation an error message, a reviewer and an agent all read [C-22, C-23].
7. Concurrency as CMU's 15-445 teaches it: know what READ COMMITTED allows, and fix read-modify-write with one atomic `UPDATE`, a row lock, a version column or SERIALIZABLE with a retry [C-37, C-38].

And the systems view: "a RDBMS may be a better choice, even for simple applications, because they offer a path forward if the application's complexity increases." (Andy Pavlo and Michael Stonebraker, "What Goes Around Comes Around... And Around...", SIGMOD Record 53(2), https://db.cs.cmu.edu/papers/2024/whatgoesaround-sigmodrec2024.pdf, June 2024).

### 8. A model ready for native listings

Three levels: the car (a vehicle, which is the duplicate group, placed in the make, model and trim catalogue), the offer (a listing, one ad on one source) and the observation (a fetch pointing at an immutable, content-addressed snapshot for crawled ads; a frozen revision for native ones) [data-model.md, Short answer]. One `listing` table serves every origin: `origin` is `external` now, Carshenas itself becomes the source `carshenas`, and a composite foreign key `(source_id, origin)` stops a listing from claiming another origin than its source; origin-specific data lives in origin-specific tables, never in polymorphic ids or a table of nullable columns [C-6]. In pass F's lab the native migration ran as one additive transaction on live crawled rows, the fingerprints of `listing`, `listing_price_event` and `snapshot` were identical before and after, and 60 of 60 constraint cases passed; the same chain passed again on PostgreSQL 18.6. CS-4's first migration creates the listing's identity and lifecycle only, with the temporary CHECK `listing_only_external_for_now` that the native migration will drop; everything the ad says about the car arrives with CS-2, CS-8 and CS-10 (`docs/design/data-model.md`).

## Disagreements, and how they were settled

- **Indexes on foreign keys.** GitLab says "when adding a foreign key, you must always add an index first" [harness.md, GL1b]; Laurenz Albe says a small referencing table needs none, nor does one never joined that way or whose parent is never deleted [LA3], and pass E recommended indexing only when needed [H-7]. The owner chose always, with exceptions named in the migration: a comment on the foreign-key constraint starting `unindexed:` says why, and a catalog test fails on any other unindexed foreign key. CS-4 has one exception, `listing_source_fk`, served by the leading column of `listing_source_key_unique`.
- **Tests.** Pass C wanted every test on a real server with a template database cloned per worker [C-53, C-54]; pass E proved fast schema tests in PGlite [harness.md, lab]. Both are used: PGlite (PostgreSQL 18.3) runs the constraint and catalog tests inside `pnpm check` with no Docker, and `pnpm db:check` runs integration tests against PostgreSQL 18.6 on a scratch database. Template cloning waits for the first tests that write concurrently (the worker, CS-6).
- **Insert handling.** `ON CONFLICT` for the crawler's and every batch write; insert-and-map the violation (`constraintViolation()`) for a person's create, where a conflict is rare and needs a Farsi message; a pre-check only for the person's convenience [C-31, C-34, H-1].
- **Crawl policy in the database.** Pass F put ADR-0008's rules into the schema, including triggers that read other rows (a crawl must cite the latest policy check; a block stops the source in the same transaction). CS-4 took the row-local rules (the three-second floor, an official-API source can never crawl, a stop records when and why) and the append-only guards; the cross-row backstops arrive with the crawler in CS-6.
- **`IF NOT EXISTS` in migrations.** Squawk's `prefer-robust-stmts` and Supabase's skill ask for it; Nikolay Samokhvalov warns that it hides drift. The rule is excluded in `.squawk.toml`: a versioned migration fails loudly when the database is not in the state it expects [H-4].
- **Vectors in their own database.** Christopher Winslett keeps vector data on a separate database because of index-build load [CD8]; pgvector, Supabase and Stephan Schmidt keep it with the rest. The owner chose the same database; HNSW build time and its effect on crawler writes are measured before any split.
- **Designing for growth.** Andrew Atkinson designs for today [AA9]; Laurenz Albe, Nikolay Samokhvalov and Andy Pavlo pay growth costs that are cheap now and expensive later. The owner took the second view where it is cheap now: `bigint` keys and one listing table with an origin, but no native tables until they are needed.
- **Phone hashes.** ADR-0008 said "salted hashes". A per-row salt makes equal numbers hash differently, which defeats matching across sites, and a stored or public salt does not stop enumerating about a billion numbers. The owner chose HMAC-SHA-256 with the key in the environment and a key version for rotation [C-61, integrity lab 15].

## Facts verified while building CS-4

Not in the passes; observed in the repository on 2026-09-27.

- **PGlite 0.5.8 runs PostgreSQL 18.3 but has no lz4**: the migrations failed with "compression method lz4 not supported" on the column-level `COMPRESSION lz4` of `snapshot.payload`, so it was dropped for `default_toast_compression = lz4` in `db/postgresql.conf`. Roles, grants and constraint errors (SQLSTATE, constraint and table) behave as on the server; a PGlite database starts in about 2 seconds, and the two schema test files run in about 4.
- **The builtin C.UTF-8 locale sorts Persian by code point**, measured on PostgreSQL 18.6: «ام‌وی‌ام بنز تویوتا هیوندای پژو چری ژیان کیا گلف یوز», with هیوندای before پژو; `COLLATE "fa-x-icu"` gives «ام‌وی‌ام بنز پژو تویوتا چری ژیان کیا گلف هیوندای یوز». The database keeps the builtin locale, which no operating-system upgrade can reorder under an index, and pages that sort Persian names use the ICU collation in the query. `lower()` and `to_tsvector('simple', …)` handled Latin and Persian text under it.
- **node-postgres surfaces a throwing type parser as a query error**: the `int8` parser that refuses values beyond `Number.MAX_SAFE_INTEGER` rejected the query with its `RangeError`, and the same connection answered the next query.
- **A BEFORE trigger rejects before CHECK constraints are evaluated**: a native listing was refused by the lifecycle trigger `listing_status_guard` (23514) before `listing_only_external_for_now` was reached, so the schema test disables the trigger inside its transaction to prove the CHECK. Likewise, deleting a listing outside a purge was refused by `fetch_log`'s append-only guard before `snapshot`'s (both 23000), in an order set by internal trigger order, so the test accepts either.
- **The ESLint SQL selectors had to be tightened**: pass E's patterns matched `update` or `with` at the start of any string, so English such as "Update failed:" tripped them. They now require SQL shapes (`UPDATE x SET`, `WITH x AS (`), a clean self-test sample proves prose passes, and they went on to catch constant SQL fragments interpolated into the repository's own catalog test, which now uses a temporary view instead.
- **Squawk lints down sections too** (`ban-drop-table` and `require-concurrent-index-deletion` fired on the down sections that drop tables and indexes), so only up sections are linted; down sections run only on development and check databases. Its `prefer-bigint-over-int` and `prefer-bigint-over-smallint` rules fire on bounded values such as an HTTP status, so they are excluded and the catalog tests check that keys and references are `bigint` or text codes.
- **The official PostgreSQL 18 image keeps data in `/var/lib/postgresql/18/docker`** and declares the volume at `/var/lib/postgresql`, so the Compose volume is mounted there. The health check probes over TCP, because during first-start initialisation the server listens on its socket only and would otherwise look ready too early.
- **dbmate's schema dump uses the host's `pg_dump`** (16 on this machine, against a server on 18), so migrations run with `--no-dump-schema` and `db/schema.sql` is dumped inside the container, with a fixed `--restrict-key` so the `\restrict` line PostgreSQL 18's `pg_dump` writes does not change from run to run.
- **A role can become the owner at login**: `ALTER ROLE carshenas_migrate SET role = 'carshenas_owner'` makes every object a migration creates belong to the owner, which cannot log in (checked in `pg_class` after a migration).
- **The health route survives the database going away**: with the container stopped it answered 503 `{"status":"unavailable"}` and logged the cause; the pool's error handler logged the dropped idle connection instead of crashing the server; after a restart the same process answered 200.
- **The catalog tests are not vacuous**: a deliberately bad migration (a serial key, a `timestamp`, a `varchar(10)`, auto-named CHECK and foreign-key constraints, an unindexed foreign key, a CHECK list without a union type) failed six of the eight catalog tests, each naming the offending object.

## Recommendation

Follow the `database` skill's checklist for every table, migration and query, and let the checks, not memory, enforce what they can: constraints and named violations for integrity, `EXPLAIN (ANALYZE, BUFFERS)` and `pg_stat_statements` before any index or performance claim, exact vector search until a measured query needs HNSW, and the catalog tests for the conventions. Revisit the thresholds in the stack note's trigger table when real listings arrive (CS-6 and CS-7), and re-measure the lab numbers on the production VPS (CS-23).
