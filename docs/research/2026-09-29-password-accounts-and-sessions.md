# How should Carshenas store passwords, keep sessions and guard sign-in for username-and-password accounts with a buyer and a superadmin role, on Next.js 16 and PostgreSQL alone, from inside Iran?

- Date: 2026-09-29
- Asked by / for: Pedrum, for CS-39 (accounts: sign-up and sign-in for buyers, sessions, and a superadmin role). The owner decided on 2026-09-29 that accounts are a username and a password only for now (no email, no phone, no one-time code; a phone number and an SMS code may come later), with two roles, buyer and superadmin; the first superadmin, `pedram`, is seeded into the database with a strong password; the superadmin role is never granted through the product's own screens; a superadmin lands on the admin dashboard after signing in.
- Outcome: a recommendation for ADR-0020 (not yet written): Argon2id through Node.js 24's own `crypto.argon2`, 15-character passwords with an offline blocklist and Persian folding, hashed 256-bit session tokens in PostgreSQL behind a `__Host-` cookie (a plain one on loopback, for WebKit), our own origin check on every Server Action, throttling per account, device and address in PostgreSQL, a bootstrap command for the superadmin with column privileges that keep the role out of the product's reach, and no auth library. Six questions for the owner at the end.

## Questions

1. Password hashing on this Node.js version: is Argon2id in Node's built-in `crypto` (which version, stable or experimental, API shape), and how does it compare with `@node-rs/argon2` and the built-in `crypto.scrypt`? Which parameters does OWASP give, how is the hash stored so parameters can be upgraded, how is it verified in constant time, how long should one hash take on a 2-core server, and how is the event loop kept free?
2. Password policy under NIST SP 800-63B-4 (final, 2025) and OWASP ASVS 5.0: minimum length when the password is the only factor, the maximum to accept, composition rules, Unicode normalisation, blocklists. Can a breached-password check run from Iran without a third-party call (bundled lists, their licences and sizes; zxcvbn-ts), and is the Have I Been Pwned range API reachable from Iran? What policy for buyers, and what stronger one for the superadmin?
3. Sessions without a library, after the Copenhagen Book and Lucia's session guide: token format, entropy, what the database stores, absolute and sliding expiry and renewal, ending sessions on sign-out, on a password change and everywhere at once, and cleaning up expired rows.
4. Cookies: the `__Host-` prefix, `Secure`, `HttpOnly`, `SameSite`, `Path`, `Max-Age`. Do Chromium, Firefox and WebKit keep `Secure` and `__Host-` cookies over plain http on `localhost` and on `127.0.0.1`, where the Playwright tests run? The safest design for development and production.
5. Cross-site request forgery in Next.js 16: what Server Actions check by themselves (Origin against Host, `serverActions.allowedOrigins`), what Route Handlers need, how `SameSite=Lax` fits; `cookies()`, `proxy.ts` and `redirect` as the version-matched documentation describes them.
6. Rate limiting and brute force with PostgreSQL and no Redis: fixed windows upserted with `ON CONFLICT`, sliding logs, token buckets; per username and per client address; throttling against lockout; credential stuffing; the client address behind a reverse proxy in Next.js 16 and what to trust; unknown usernames handled in the same time (a dummy hash) and wording that does not reveal which usernames exist, while sign-up must say whether a name is free.
7. A library or our own code, judged against Next.js 16 App Router, Server Actions, Kysely on node-postgres, our own SQL migrations and naming rules, no SaaS, Farsi errors, a later phone-and-SMS sign-in and roles: Better Auth, Auth.js v5, iron-session, self-hosted identity servers (Ory Kratos, Keycloak, Zitadel), and SaaS (Clerk, Auth0, Supabase Auth, WorkOS) only to rule them out for Iran.
8. Bootstrapping the first superadmin (a command that reads or generates the password and never takes it as an argument, an idempotent upsert, a record of every role grant), and keeping a role check on every page and action in Next.js 16 (a `requireRole` in the data layer, not only in `proxy.ts`).

## Findings

### 1. Password hashing

**Node.js has Argon2 built in since 24.7.0, and it is stable, but not on Node 22** (via sub-agent; the docs and changelog spot-checked here with `curl` on the `v24.x` and `v22.x` branches):

- `crypto.argon2(algorithm, parameters, callback)` and `crypto.argon2Sync()` arrived in v24.7.0 (2025-08-27; PR #50353 by Ranieri Althoff, the author of the `argon2` npm package), first marked "1.2 - Release candidate". PR #63924, "doc,crypto: mark argon2 and encap/decap as stable", shipped in v26.4.0 (2026-06-24) and v24.19.0 LTS (2026-08-03). The `v22.x` docs mention Argon2 nowhere; nothing was backported. This machine's Node.js 22.14.0 has no `crypto.argon2` (checked here).
- Parameters, from the docs: `message` (the password), `nonce` ("must be at least 8 bytes long. This is the salt"; 16 random bytes recommended), `parallelism`, `tagLength`, `memory` ("memory cost in 1KiB blocks"), `passes`, and optional `secret` ("This is known as pepper") and `associatedData`. It is callback-only and returns the raw tag: encoding a PHC string, parsing it back and comparing are ours to write.
- It needs OpenSSL 3.2 or later (`deps/ncrypto/ncrypto.h`); a Node.js built against an older system OpenSSL exports the function but throws `ERR_CRYPTO_ARGON2_NOT_SUPPORTED` when called, so `typeof crypto.argon2` proves nothing. The official Node.js 24.21.0 binary carries OpenSSL 3.5.8 (measured).
- The async call runs on libuv's thread pool (`CryptoJob` is a `ThreadPoolWork`). A fix that stops Argon2 from spawning its own threads (#66237, 2026-09-22) is unreleased and affects only `parallelism > 1`.
- Release lines on 2026-09-29 (Node.js Release Working Group): 22.x is Maintenance LTS until 2027-04-30; 24.x is Active LTS (maintenance from 2026-10-20, end of life 2028-04-30); 26.x becomes LTS on 2026-10-28. The repository says `"node": ">=22"`; CI already runs Node.js 24 (the Playwright image `mcr.microsoft.com/playwright:v1.63.0-noble` installs `NODE_VERSION=24`, read here in `utils/docker/Dockerfile.noble`), and ADR-0016 already needs 22.15 or later for OpenTelemetry SDK 3, above this machine's 22.14.0.

**The libraries** (via sub-agent, from the npm registry and their sources):

- `@node-rs/argon2` 2.2.1 (2026-09-10, MIT, napi-rs's author): PHC strings, `verify`, `parseOptions` for "needs rehash" checks, defaults exactly OWASP's `m=19456, t=2, p=1`, prebuilt binaries for Linux glibc and musl. **Its engine changed seven weeks ago**: 2.1.0 (2026-08-13) replaced RustCrypto's `argon2` 0.5 with `argon2-rust`, a new crate by the same author first published on 2026-08-10 (repository created 2026-07-31); no audit was found. Its `Algorithm` is a `declare const enum` that fails TypeScript's `isolatedModules`, which Next.js sets.
- `argon2` 0.45.1 (2026-07-21, MIT): the reference C implementation behind `Napi::AsyncWorker`, prebuilt binaries, `hash`, `verify` and `needsRehash`; its README says it will become "a minimal wrapper" over Node's own once every supported Node.js release has it (`argon2@1.0.0-alpha.1` already requires Node.js 24.7.0).
- Pure JavaScript or WebAssembly (`hash-wasm`) runs on the calling thread: up to 86.7 ms between timer ticks in the lab. `@noble/hashes` says Argon2 "can't be fast in JS" and suggests scrypt.
- `crypto.scrypt` is built into every line, but OWASP's `N=2^17, r=8` needs 128 MiB per call, four times the default `maxmem` (32 MiB), and took 320 to 400 ms in the lab.

**Parameters and format** (OWASP Password Storage Cheat Sheet, repository copy of 2026-09-05; RFC 9106; the PHC string specification, now at C2SP; via sub-agent):

- OWASP: "Use Argon2id with a minimum configuration of 19 MiB of memory, an iteration count of 2, and 1 degree of parallelism", or the equal-strength sets `m=47104, t=1`, `m=12288, t=3`, `m=9216, t=4`, `m=7168, t=5` (all `p=1`); "calculating a hash should take less than one second"; a work factor set too high lets "an attacker … carry out a denial of service attack by exhausting the server's CPU"; to raise it, "wait until the user next authenticates, then re-hash their password with the new work factor". A pepper is "additional defense in depth (though alone, it provides no additional secure characteristics)", "should not be stored along with the generated hash", and changing it forces resets.
- RFC 9106 §4 recommends `t=1, p=4, m=2 GiB` first and `t=3, p=4, m=64 MiB` second, or choosing memory and time a server can afford; salt "16 bytes is RECOMMENDED".
- PHC string: `$argon2id$v=19$m=19456,t=2,p=1$<salt>$<hash>`, standard Base64 without `=` padding, parameters in the order `m,t,p`, a 16-byte salt and a 32-byte hash by default. The lab's hand-encoded `node:crypto` string verified in `@node-rs/argon2`, and the reverse.
- Comparison: `crypto.timingSafeEqual` needs equal lengths and throws otherwise; the timing that actually leaks is answering faster for an unknown username, which a dummy verification removes (section 6).

**Lab** (via sub-agent, `scratchpad/lab-hashing/`, on an i7-10510U laptop under background load; a budget VPS core is likely slower, not measured):

| Setting | Median of one hash |
|---|---|
| `@node-rs/argon2`, `m=19456, t=2, p=1` | 18 to 22 ms (verify 17 to 24 ms) |
| `argon2` 0.45.1, same | 31 to 40 ms |
| `node:crypto` on Node.js 24.21.0, same | 38 to 48 ms |
| `node:crypto`, `m=65536, t=3, p=1` | 238 ms |
| `crypto.scrypt`, `N=2^17, r=8, p=1` | 320 to 400 ms |

Sixteen simultaneous hashes on two cores (`taskset -c 0,1`, pool of four): the event loop stayed responsive (p99 delay about 2 to 3.5 ms above idle), but an unrelated `fs.stat` waited up to 150 ms (430 ms with `node:crypto`) because hashes held every pool thread. With at most two hashes at a time, the same probe waited 2 to 5 ms, throughput stayed about 70 to 80 hashes a second with `@node-rs/argon2`, and memory growth halved. `node:crypto`'s resident memory settled 134 MiB higher after 16 hashes (glibc keeping freed blocks in per-thread arenas; about 20 MiB with `MALLOC_ARENA_MAX=1` or a single pool thread), a plateau, not a leak. pilcrow's Auth book asks the same of Node.js (read here in the downloaded page): "In a single-threaded environment like JavaScript, ensure that hashing is offloaded to a separate process and properly queued. In multi-threaded environments, limit the number of concurrent hashing operations using a mutex or semaphore"; the async call already runs off the main thread, so the queue is what remains to build.

### 2. Password policy

**NIST SP 800-63B-4 §3.1.1.2** (final, July 2025 per CSRC; read here):

- "Verifiers and CSPs SHALL require passwords that are used as a single-factor authentication mechanism to be a minimum of 15 characters in length", and may allow shorter ones "only used as part of multi-factor authentication processes", but at least eight. A password is our only factor, for buyers and for the superadmin: password-only accounts are AAL1, since AAL2 needs two factors.
- "SHOULD permit a maximum password length of at least 64 characters"; "SHOULD accept all printing ASCII … characters and the space character" and Unicode; "Each Unicode code point SHALL be counted as a single character"; "SHALL NOT impose other composition rules"; no periodic change, but "SHALL force a change if there is evidence that the authenticator has been compromised"; no hints or security questions; "SHALL verify the entire submitted password (e.g., not truncate it)".
- **Normalisation changed to NFC**: "If Unicode characters are accepted in passwords, the verifier SHOULD apply the normalization process for stabilized strings using the Normalization Form Canonical Composition (NFC) … before hashing", and users "SHOULD be advised that some endpoints may represent some characters differently". The previous revision said NFKC or NFKD. RFC 8265 (2017) also uses NFC for passwords, and maps "Any instances of non-ASCII space" to U+0020.
- **Blocklist**: "SHALL compare the prospective secret against a blocklist that contains known commonly used, expected, or compromised passwords. The entire password SHALL be subject to comparison, not substrings", for example breach corpuses, dictionary words and "Context-specific words, such as the name of the service, the username, and derivatives thereof"; the verifier "SHALL provide the reason for rejection"; "Excessively large blocklists are of little incremental security benefit", and the list "only needs to include entries that meet" the minimum length (Appendix A.3, via sub-agent).
- Usability (via sub-agent): "SHALL allow the use of password managers and autofill"; paste SHOULD be permitted; "SHOULD offer an option to display the password".
- Storage (via sub-agent): "salted and hashed using a suitable password hashing scheme", a salt of "at least 32 bits", a cost "as high as practical", and a pepper as a SHOULD: "an additional iteration of a keyed hashing or encryption operation using a secret key known only to the verifier", the key "stored separately".

**OWASP ASVS 5.0.0** (May 2025; requirement rows read here in `5.0/en/0x15-V6-Authentication.md` and `0x16-V7-Session-Management.md`, the rest via sub-agent):

| Requirement | Level | Text |
|---|---|---|
| 6.2.1 | 1 | "passwords are at least 8 characters in length although a minimum of 15 characters is strongly recommended" |
| 6.2.3 | 1 | "password change functionality requires the user's current and new password" |
| 6.2.4 | 1 | checked "against an available set of, at least, the top 3000 passwords which match the application's password policy, e.g. minimum length" |
| 6.2.8 | 1 | "verifies the user's password exactly as received from the user, without any modifications such as truncation or case transformation" |
| 6.2.9, 6.2.12 | 2 | at least 64 characters permitted; checked against breached passwords |
| 6.3.1 | 1 | controls against "credential stuffing and password brute force", which per the sub-agent must also "prevent malicious account lockout" |
| 6.3.2 | 1 | no default accounts ("root", "admin", or "sa") |
| 6.3.3 | 2 | multi-factor authentication; relaxing it needs a documented rationale |
| 7.2.3 | 1 | reference tokens from a CSPRNG with "at least 128 bits of entropy" |
| 7.3.2 | 2 | an absolute session lifetime "according to risk analysis" |
| 7.4.2 | 1 | disabling or deleting an account ends all its sessions |
| 7.4.3 | 2 | "the option to terminate all other active sessions after a successful change" of a password |
| 3.3.1, 3.3.3, 3.3.4 | 1, 2, 2 | cookies `Secure` with `__Host-` or `__Secure-`; `__Host-`; `HttpOnly` |

**Practice** (via sub-agent): GitHub accepts "Eight characters long, if it includes a number and a lowercase letter, or 15 characters long with any combination"; Microsoft Entra ID requires 8 to 256 characters and three of four character types, and no Unicode; Google accepts only ASCII and recommends at least 12. Services still impose composition rules and ASCII; the standards no longer do.

**Breached and common passwords without a call abroad** (via sub-agent unless marked):

- Have I Been Pwned's range API needs no key and has no rate limit, and the Pwned Passwords data carries no licence or attribution requirement; the full set is about 2.07 billion SHA-1 hashes, about 40 GB compressed, and the official downloader fetches it through the same API, prefix by prefix. The API is served by Cloudflare.
- **From Iran, any foreign API is unreliable, filtering aside.** OONI has no measurement of `haveibeenpwned.com` or `api.pwnedpasswords.com` from Iran (2020-01-01 to 2026-09-29), so reachability on a normal day is unknown. The shutdowns are documented: November 2019 (OONI and CAIDA: Iranians "had access to Iran's national Intranet" only); 13 to 25 June 2025 (Cloudflare Radar, access "limited to … 'National Information Network'"); 8 to 21 January 2026 (Cloudflare, Kentik: whitelisting "allows only approved users or services"); and an 88-day shutdown from 28 February to 26 May 2026 (Cloudflare Radar, traffic "well under 1% of previous levels"). A sign-up that calls abroad fails for months at a time.
- SecLists (MIT) has no Persian list. **Lab** (via sub-agent): the union of its NCSC 100k, Pwdb top-1M and xato top-1M lists holds 1,643,494 entries after NFC; 914,991 have at least 8 characters (3.4 MB gzipped, or a 1.64 MB Bloom filter at a 0.1% false-positive rate), and only **16,135 have at least 15 (134 KB gzipped)**, still above ASVS's top 3,000. A 15-character minimum turns the blocklist into a small file.
- zxcvbn-ts 4.2.0 (2026-08-12, MIT, maintained) has a `language-fa` package (96 KB gzipped) whose dictionaries are Latin transliterations only (no Persian script) and no Persian keyboard graph; "password" typed with the Persian layout on ("حشسسصخقی") scored 2 of 4. Dropbox's original zxcvbn has been unmaintained since 2017.
- Iranian habits (via sub-agent): Alebouyeh and Bidgoly (*J Comput Virol Hack Tech* 18(2), 2022, abstract) found Iranian users "more inclined to use numeric passwords". Windows' "Persian (Standard)" layout types Persian digits while the legacy "Persian" layout types ASCII digits (Microsoft layout files, kbdlayout.info), and 98.8% of the NCSC list is typed entirely on keys the Persian layout remaps, so a common Latin password typed with the wrong layout active slips past a plain blocklist.
- **Lab** (here, Node.js 22.14.0): NFC and NFKC both leave Persian digits (U+06F1), Arabic-Indic digits (U+0661), Arabic yeh (U+064A) and kaf (U+0643) unchanged, so neither unifies ی/ي, ک/ك or ۱/1; NFKC, not NFC, folds fullwidth digits, the no-break space and Arabic presentation forms (U+FEFB to لا). A password typed with Persian digits on one device and ASCII digits on another fails under NIST's normalisation. The search normaliser folds exactly these characters (ADR-0011) and every typed number is folded to Latin digits (ADR-0014), but folding a password before hashing is a "modification" in ASVS 6.2.8's words and can never be undone for stored hashes.
- bcrypt reads at most 72 bytes; a Persian letter is two bytes in UTF-8, so a Persian passphrase is cut after 36 letters, against NIST's "SHALL verify the entire submitted password" (via sub-agent, from the OWASP cheat sheet).

### 3. Sessions

**The two guides the question names have both moved on** (via sub-agent, from the sites and their repositories):

- **The Copenhagen Book is archived.** Its pages say "This website has been replaced and is no longer maintained", pointing to pilcrow's "Auth book" (auth.pilcrowonpaper.com, pages last changed 2026-06-02 to 06-05); the repository was archived on 2026-06-03. What it said, last edited 2024 to 2025: tokens "should have at least 112 bits of entropy (120-256 is a good range)"; "Session IDs can be hashed before storage", sensitive tokens with SHA-256; sessions "expire in 30 days by default, but the expiration gets pushed back 30 days when it's used within 15 days before expiration", or one hour extended every 30 minutes with "an absolute expiration of 12 hours"; "All sessions of the user should also be invalidated when they gain new permissions (email verification, new role, etc) or change passwords"; against fixation, "always creating a new session when the user signs in".
- **The Auth book** recommends "generating both an ID and a secret for your sessions", a 32-byte secret hashed with SHA-256 and compared "using a constant-time comparison"; refreshing expiry "periodically (e.g., once an hour or once per day) rather than on every request"; and, reversing the Copenhagen Book, asking "users whether they want to sign out of all devices immediately after changing their password, but it shouldn't be mandatory". On throttling it proposes a token bucket per user ("a maximum token capacity of 5 and a refill rate of 1 token per minute"), says to "avoid implementing account lockouts or exponential throttling" and "strict IP-based rate limits"; and he "would not fully recommend" one error for a missing account and a wrong password, because "differences in response time can be used to infer whether a user exists" and sign-up leaks existence anyway (read here in the downloaded page). It is one author's opinion, with no licence on the repository.
- **Lucia** was deprecated by its author, pilcrow ("It's official - I'll be deprecating Lucia v3 by March 2025", discussion #1714, 2024-10-20; the reason: "One word - database… adapters limit the API"). Since 2026-07-29 the site holds a single file, `code/auth_session.ts` (0BSD; read here with `curl`): the token is `id + "." + secret.toBase64()`, an 80-bit id and a 32-byte secret from `crypto.getRandomValues`; the database keeps `secret_hash`, the SHA-256 bytes, compared by an XOR-loop `constantTimeEqual`; a session expires 10 days after `token_last_verified_at`, which is refreshed at most once an hour; `created_at` is stored but never checked, so there is no absolute limit; the cookie is `Path=/`, `Expires`, "Secure (if your website uses HTTPS)", `HttpOnly`, `SameSite=Lax`; a `Sec-Fetch-Site` check guards non-GET requests. `Uint8Array.toBase64` needs Node.js 25, so the file does not run on 22 or 24 as written.
- **Why the token has two parts.** Lucia's late-2024 guide made "The session ID … SHA-256 hash of the token" (20 random bytes in base32, 30 days, extended when fewer than 15 remain). PR #1802 (2025-06-08) split it: "We're using a separate ID and secret to prevent any possibility of a timing attacks", while its migration page admits that for SQL `=` "there hasn't been a successful recorded attack". Looking a row up by the hash of the whole token and looking it up by a public id, then comparing a secret's hash in constant time, are both defensible; the second removes the argument.
- Lucia's 2025 Next.js page wrapped `getCurrentSession` in React `cache()` and, because "You cannot set cookies with `cookies()` … when rendering routes", had middleware re-set the cookie with a one-year `maxAge` on GET requests; its Origin snippet compared the header with a bare host, a bug, since `Origin` carries the scheme.

**Standards on lifetime and invalidation:**

- NIST SP 800-63B-4 (final, July 2025; read here): at AAL1 "A definite reauthentication overall timeout SHALL be established, which SHOULD be no more than 30 days at AAL1. An inactivity timeout MAY be applied but is not required"; at AAL2 the overall timeout "SHOULD be no more than 24 hours" and "The inactivity timeout SHOULD be no more than 1 hour". "Session secrets that are used as bearer tokens for session management SHOULD NOT be persistent (i.e., retained across a restart of the associated application or a reboot of the host device)"; the secret "SHALL be generated by the session host in direct response to an authentication event"; and "POST/PUT content SHALL contain a session identifier that the RP SHALL verify to protect against cross-site request forgery (CSRF)", a stricter rule than any framework applies (section 5).
- OWASP Session Management Cheat Sheet (last changed 2026-08-13; via sub-agent): at least 64 bits of entropy, 128 bits from a CSPRNG for home-made ids; idle timeouts of "2-5 minutes for high-value applications and 15-30 minutes for low risk applications", absolute timeouts "between 4 and 8 hours", and "All sessions should implement an absolute timeout"; renew the id after "password changes, permission changes, or switching from a regular user role to an administrator role"; `__Host-` "Recommended for session IDs"; set `SameSite` explicitly; non-persistent cookies; a visible sign-out, `Cache-Control: no-store` and `Clear-Site-Data` on sign-out; let users see and end their sessions. OWASP Authentication Cheat Sheet: changing a password requires "Current password verification"; after re-authentication, "Invalidate sessions … and rotate tokens". Forgot Password Cheat Sheet: "Ask the user if they want to invalidate all of their existing sessions, or invalidate the sessions automatically."
- The Next.js 16 guide calls database sessions "more secure" than stateless ones and recommends a library for either; its example stores a database id (section 5).
- Advisories that show why the check must sit next to the data (via sub-agent, GitHub Advisory Database): CVE-2025-29927 (GHSA-f82v-jwr5-mffw, 2025-03-21, critical, CVSS 9.1) let a request "bypass authorization checks … if the authorization check occurs in middleware" with an `x-middleware-subrequest` header; five more Proxy-bypass advisories followed in 2026 (CVE-2026-44573, -44574, -44575, -45109, -64642), whose workaround is to "enforce authorization in the underlying route or page logic"; and CVE-2026-27978 (GHSA-mq59-m269-xvcx, 2026-03-17) treated `Origin: null` as a missing origin and let a Server Action through, fixed in 16.1.7, with "Add CSRF tokens for sensitive Server Actions" among its workarounds. 16.3.5 is above every patched version.

### 4. Cookies

**The standard** (via sub-agent): RFC 6265bis is still a draft, draft-ietf-httpbis-rfc6265bis-22 (2025-12-01), approved by the IESG on 2025-12-02 and in the RFC Editor's queue. A `__Secure-` cookie "will have been set with a Secure attribute"; a `__Host-` cookie also has "a Path attribute with a value of /, and no Domain attribute", and is accepted only "if set from a secure origin"; "most user agents consider 'https' to be a scheme that denotes a secure protocol and 'localhost' to be trusted host", and the draft now "Considers potentially trustworthy origins as 'secure'" (httpwg PR #2759, 2024-03-13). `SameSite=Lax` sends a cookie cross-site only on "top-level navigations which use a 'safe' … HTTP method"; expiry is capped at 400 days (Chrome since M104, 2022, "Cookie Expires and Max-Age attributes now have upper limit"). NIST SP 800-63B-4 (read here) wants session cookies that are "accessible only on secure (i.e., HTTPS) sessions", `HttpOnly`, with "the '__Host-' prefix and set 'Path=/'", "SameSite=Lax" or "SameSite=Strict", an expiry "at or soon after the session's validity period", which "SHALL NOT be relied upon to enforce session timeouts", and "only an opaque string". MDN's compatibility data: `SameSite=Lax` is the default only in Chrome 80+ and Edge 86+, not in Firefox or Safari, so the attribute must be written out.

**Loopback over http, by engine** (via sub-agent, from the engines' sources and bug trackers):

- Chromium accepts `Secure` cookies from potentially trustworthy URLs since M89 (commit bd04d787, bug 1056543, 2020-11-17) and `__Host-`/`__Secure-` on localhost since M138 (CL 6535909, merged 2025-05-14); loopback IP literals count as localhost.
- Firefox accepts them since 75 (bug 1618113, 2020-03-02), for "localhost", 127.0.0.0/8 and [::1].
- Safari 27 (release notes, 2026-09-14): "Added support for secure cookies on loopback hosts", Cocoa builds on macOS 26 or later (WebKit commit 310542@main); whether it accepts `__Host-` there is UNVERIFIED. WebKit bug 232088 remains open for the general case.
- WebKit on Linux, which Playwright runs, stores cookies through libsoup, which refuses a secure cookie over any scheme but `https` and `wss` (`soup-cookie-jar.c`). Playwright's maintainer Dmitry Gozman: "Browsers have opinions on how to treat 'Secure' cookies sent over http. For example, our WebKit ignores them" (issue #5215, 2021-02-02); #35712, "Secure cookies not restored in Webkit", was closed as not planned on 2025-04-23 (both read here with `gh`).

**Lab: what each engine keeps over plain http** (2026-09-29, `scratchpad/lab-cookies/cookies-lab.mjs`, not committed). A Node.js server on port 3977, listening on 127.0.0.1 and ::1, answered `/set` with eight `Set-Cookie` headers and `/echo` with the `Cookie` header it received; each engine of Playwright 1.63.0 (the repository's pinned version) opened `/set` then `/echo` in a fresh context, first as `http://localhost:3977`, then as `http://127.0.0.1:3977`.

| Cookie (all `Path=/; HttpOnly`) | Chromium 153 | Firefox 155 | WebKit 26.6 (Playwright's Linux build) |
|---|---|---|---|
| no `Secure`, `SameSite=Lax` | kept, both hosts | kept, both hosts | kept, both hosts |
| `Secure; SameSite=Lax` | kept, both hosts | kept, both hosts | **refused**, both hosts |
| `__Secure-…; Secure` | kept, both hosts | kept, both hosts | **refused**, both hosts |
| `__Host-…; Secure` (with or without `Max-Age`) | kept, both hosts | kept, both hosts | **refused**, both hosts |
| `__Host-…` without `Secure` | refused | refused | refused |
| `__Host-…; Secure; Domain=localhost` | refused | kept on `localhost`, refused on `127.0.0.1` | refused |
| `Secure; SameSite=Strict` | kept, both hosts | kept, both hosts | **refused**, both hosts |

So Chromium and Firefox treat both loopback names as secure for cookies; Playwright's WebKit keeps no `Secure` cookie over http on either name. That matters here: the CI job sets `E2E_WEBKIT: '1'` (`.github/workflows/e2e.yml`), so the `iphone` project runs the suite in WebKit against a production build at `http://127.0.0.1:3100`. A `__Host-` session cookie would sign nobody in there. Desktop Safari was not tested.

### 5. Cross-site request forgery, cookies and redirects in Next.js 16.3.5

Read here in the version-matched docs (`apps/web/node_modules/next/dist/docs/`) and the compiled source of 16.3.5; Context7's `/vercel/next.js/v16.2.9` says the same.

- **Server Actions check the origin themselves.** "To prevent CSRF attacks, Next.js compares the host in a request's `Origin` header against the app's own host, taken from `x-forwarded-host` or `host`, and rejects the action when the two differ. If not provided, only the same origin is allowed. A request that carries no `Origin` header at all is allowed through with a warning rather than rejected" (`serverActions.md`, `allowedOrigins`). The source (`dist/server/app-render/action-handler.js`, around line 440) matches: a missing `Origin` only logs a warning, because "handcrafted requests can't contain user credentials that haven't been shared willingly"; `Origin: null` is compared as the host `null` and refused unless listed; a refused fetch action ends with a 500 and "Invalid Server Actions request." Only `POST` invokes an action (`data-security.md`). The same check covers the sign-in form, so an attacker cannot sign a visitor into the attacker's account (login CSRF) through it.
- **`allowedOrigins` is for proxies that hide the public host.** "Behind a reverse proxy, no entry is needed as long as the proxy forwards the public host in `x-forwarded-host`" (`serverActions.md`). Next.js fills `x-forwarded-host` from `host` only when the header is absent (`dist/server/base-server.js`, line 609), so the reverse proxy must pass the public `Host` (nginx: `proxy_set_header Host $host`).
- **The check is not authorisation.** "Framework protections are not a substitute for application-level checks. Inside every action: Authenticate and authorize. Render-time gating (only rendering a form on an authenticated page) is not a security boundary, because requests can be sent without going through the UI" (`02-guides/server-actions.md`).
- **Route Handlers get no origin check.** The repository already answers 403 to a `POST /api/client-errors` whose `Sec-Fetch-Site` is present and not `same-origin` (`apps/web/src/server/observability/browser-errors.ts`); any state-changing Route Handler needs the same.
- **`SameSite=Lax`, stated explicitly.** Chrome's temporary "Lax + POST" exception, which sends a cookie up to two minutes old on a cross-site top-level POST, "is an intervention for Lax-by-default cookies (cookies that don't specify a `SameSite` attribute)" (Chromium, "SameSite Updates", entry of 2019-11-01). A cookie that says `SameSite=Lax` is never sent on a cross-site POST, so it is a second, independent layer behind the origin check, but only a layer: the cookie draft says Lax "provides reasonable defense in depth against CSRF attacks that rely on unsafe HTTP methods (like POST), but does not offer a robust defense against CSRF as a general category of attack" (draft-ietf-httpbis-rfc6265bis-22 §5.6.7.1).
- **Where cookies can be written.** `cookies()` is async; "Setting cookies is not supported during Server Component rendering. To modify cookies, invoke a Server Function from the client or use a Route Handler", and "HTTP does not allow setting cookies after streaming starts" (`cookies.md`). A session that slides forward therefore cannot rewrite its cookie while a page renders.
- **Cache Components (on in this app, ADR-0003).** "With Cache Components, calling `cookies()` outside of a `<Suspense>` boundary prevents the route from being prerendered" (`cookies.md`); the guide *Authentication with Cache Components* adds "reading `cookies()` outside a boundary is a build error" and "Keep the session read out of a layout's top level, too", and warns that arguments and `cacheTag` values of cached functions "are stored in plain text", so no token may reach a cache key.
- **Proxy is an optimisation, never the guard.** Server Functions "are handled as POST requests to the route where they are used, so a Proxy matcher that excludes a path will also skip Server Function calls on that path. A matcher change or a refactor that moves a Server Function to a different route can silently remove Proxy coverage. Always verify authentication and authorization inside each Server Function rather than relying on Proxy alone" (`proxy.md`). The authentication guide: Proxy "should not be your only line of defense", and it should "only read the session from the cookie (optimistic checks), and avoid database checks". Proxy runs on Node.js by default since 16.0.0.
- **Layouts do not guard pages.** "Due to Partial Rendering, be cautious when doing checks in Layouts as these don't re-render on navigation", and "A layout also does not control whether the rest of the route renders … a layout that hides or swaps them does not stop them from running or from appearing in the RSC Payload" (`authentication.md`, "Layouts and auth checks"). Its recommendation is a Data Access Layer: a `verifySession()` wrapped in React `cache`, called by every data request, Server Action and Route Handler.
- **The guide's own database-session example stores a database id** and puts it, encrypted, in the cookie ("Encrypt the session ID before storing it in the user's browser"), with `httpOnly`, `secure: true`, `sameSite: 'lax'`, `path: '/'`. That design rests on a server key; ADR-0013 point 2 ("Anything whose possession grants access is a random token stored hashed, never an id") and the session guides in section 3 rest on a random secret instead.
- **`redirect()`.** In a Server Action it "performs a client-side navigation when JavaScript is available. For progressive enhancement form submissions, it serves a 303"; it throws, so it is called outside `try`; and it "also accepts absolute URLs and can be used to redirect to external links" (`redirect.md`, `redirecting.md`), so a "return to where you were" value must be checked as a path on this site (an open redirect otherwise).
- **`authInterrupts`** (`forbidden()`, `unauthorized()`) is still experimental in 16.3.5 (`authInterrupts.md`); `notFound()` is stable, and CS-40 wants a 404 for non-superadmins anyway.

### 6. Rate limiting and brute force

**What the guidance asks for.**

- NIST SP 800-63B-4 §3.2.2 (read here): "the verifier SHALL limit consecutive failed authentication attempts using a specific authenticator on a single subscriber account to no more than 100 by disabling that authenticator", and a disabled authenticator must be bound again through account recovery. To keep attackers from locking the real user out it lists, as MAY: a bot challenge; "Requiring the claimant to wait after a failed attempt for a period of time that increases as the subscriber account approaches its maximum allowance for consecutive failed attempts (e.g., 30 seconds up to an hour)"; and risk signals such as "the claimant's IP address, geolocation, timing of request patterns, or browser metadata". After a success the verifier "SHOULD disregard any previous failed attempts".
- OWASP Authentication Cheat Sheet (read here): "The counter of failed logins should be associated with the account itself, rather than the source IP address, in order to prevent an attacker from making login attempts from a large number of different IP addresses"; a lockout has a threshold, an observation window and a duration; "some applications use an exponential lockout, where the lockout duration starts as a very short period (e.g., one second), but doubles after each failed login attempt"; and "Care must be taken to prevent it from being used to cause a denial of service by locking out other users' accounts."
- OWASP Credential Stuffing Prevention Cheat Sheet (read here): blocking addresses "should not be used as the sole or primary defense due to the ease in circumvention", since toolkits spread requests over proxy networks. Its "Require Unpredictable Usernames" section applies to us directly: stuffing relies on "the re-use of usernames", credential lists "often contain only email addresses", so a site-specific username already makes a leaked email-and-password pair useless here.
- OWASP, "Slow Down Online Guessing Attacks with Device Cookies" (Anton Dedov, read here): a browser that once signed in successfully holds a signed cookie (`LOGIN,NONCE,HMAC(secret-key, "LOGIN,NONCE")`); failures from that cookie are counted for that cookie alone, while failures from unknown clients share the account's counter and are locked out after N in time T. The attacker locks out only other strangers, never the owner's known device.
- The dissent, pilcrow's Auth book (read here in the downloaded page): "A rate limit of 1 attempt per minute per user is a good starting point", a token bucket of capacity 5 refilled at 1 a minute, which "caps an attacker at roughly 500,000 attempts per year"; "I would avoid implementing account lockouts or exponential throttling as these can be easily abused to indefinitely lock out legitimate users", nor "strict IP-based rate limits", which "can accidentally block legitimate users on shared networks". The passage does not address NIST's 100-failure limit.
- Practice: Microsoft Entra ID's smart lockout locks after 10 failures for one minute, longer after each further failure, keeps separate counters for familiar and unfamiliar locations, and "tracks the last three bad password hashes to avoid incrementing the lockout counter for the same password" (Microsoft Learn, updated 2026-06-05). GitLab without email verification: "All accounts lock after 10 or more failed attempts. These accounts unlock automatically after 10 minutes" (docs.gitlab.com, "Locked user accounts").

**Algorithms that fit PostgreSQL** (no Redis, ADR-0011):

| Design | Rows per key | Accuracy | Notes |
|---|---|---|---|
| Fixed window: `INSERT … ON CONFLICT … DO UPDATE SET n = n + 1 RETURNING n` | 1 (reset when the window has passed) | Up to twice the limit across a window boundary | One atomic statement: `ON CONFLICT DO UPDATE` "guarantees an atomic INSERT or UPDATE outcome … even under high concurrency" (PostgreSQL 18, `INSERT`) |
| Sliding log: a row per attempt, counted over the last window | One per attempt | Exact | Count and insert race unless serialised; most writes; needs pruning |
| Sliding-window counter: previous window × overlap + current window | 2 | Cloudflare measured "0.003% of requests have been wrongly allowed or rate limited" over 400 million requests (Cloudflare blog, 2017-06-07) | Two fixed windows read together |
| GCRA or token bucket: one "next allowed time" per key | 1 | Exact, smooth | ADR-0018 already paces crawl lanes this way (Brandur Leach, "Rate limiting, cells, and GCRA") |
| Consecutive-failure counter with a growing wait | 1 | Exact per key | The lockout of OWASP and Entra; reset on success |

Counting attempts *before* the password is checked, in the same atomic upsert, is what keeps a burst of parallel guesses from all passing a "not blocked yet" read: every request takes its number first. **Lab** (PGlite 0.5.8, PostgreSQL 18.3, 2026-09-29, `scratchpad/lab-grants/grants-lab.mjs`, not committed): the fixed-window upsert, run three times as a role with only `SELECT, INSERT, UPDATE` on the table, returned 1, 2 and 3 on one row whose window start came from `date_bin('15 minutes', now(), …)`.

**The client address.**

- MDN, `X-Forwarded-For` (read here): "If the server can be directly connected to from the internet — even if it is also behind a trusted reverse proxy — no part of the `X-Forwarded-For` IP list can be considered trustworthy or safe for security-related uses"; with one reverse proxy, "the rightmost address should be used"; multiple headers form one list.
- Next.js 16.3.5 sets `req.headers['x-forwarded-for'] ??= socket.remoteAddress` (`dist/server/base-server.js`, line 612, read here): a value the client sent is kept as it is, and only an absent header is filled in. Behind no proxy, every visitor can therefore choose their own address; `request.ip` was removed in Next.js 15 ("provided by your hosting provider", upgrade guide).
- nginx: `$proxy_add_x_forwarded_for` is "the X-Forwarded-For client request header field with the `$remote_addr` variable appended to it", so it passes the client's own claims on, while `proxy_set_header X-Forwarded-For $remote_addr` replaces them; behind a CDN, `set_real_ip_from` with `real_ip_recursive on` takes "the last non-trusted address" (nginx docs, read here).
- IPv6: express-rate-limit, the most used Node.js limiter, keys IPv6 clients by their /56 by default because "ISPs that support IPv6 give each of their customers a range of IPv6 addresses … A malicious user could iterate through their range of IPv6 addresses and bypass simple IP-based rate limiting" (its configuration reference, read here).
- Shared addresses: Iran's two large mobile operators, MCI (AS197207) and Irancell (AS44244), use carrier-grade NAT according to Filterwatch's report of 2026-01-05 (UNVERIFIED: seen in a search result; the page answered 403 to this session). Many buyers may share one address, so limits per address must count failures, stay generous, and never lock an account.
- Development and the e2e suite run without a proxy, so every Playwright worker signs in from 127.0.0.1: the per-address limits must be configurable, or parallel tests throttle each other.

**Unknown usernames and wording.** OWASP Authentication Cheat Sheet: "An application must respond with a generic error message regardless of whether: The user ID or password was incorrect. The account does not exist", the correct form being "Login failed; Invalid user ID or password", and the code should "go through the same process no matter what the user or the password is", i.e. verify against a stored dummy hash when the username is unknown. It asks the same for registration, but that advice assumes an email that can carry the answer: with a username and nothing else, sign-up must say "taken", so usernames are enumerable by design and the defence is limiting sign-up attempts per address, never secrecy of usernames. The superadmin's username `pedram` is known in any case.

### 7. Libraries, identity servers and SaaS

Via sub-agent from the published packages (`npm pack`), the GitHub API and advisory database, and the vendors' pages; the Better Auth claims marked "spot-checked" were read here in the 1.7.6 tarball or through Context7 (`/better-auth/better-auth`).

**Better Auth 1.7.6** (2026-09-24, MIT; acquired by Vercel on 2026-07-07, "The library remains free and open source under MIT"; it has maintained Auth.js since 2025-09-22):

- **It cannot make a user without an email.** The core `user` table has `email` "unique: true, required: true" with the comment "TODO(#9124): drop required+unique in v2" (spot-checked in `packages/core/src/db/get-tables.ts`), and `name` is required too. The docs: "Email is a key part of Better Auth, required for all users regardless of their authentication method." The username plugin has no sign-up of its own; it hooks `/sign-up/email`, whose body requires `email`. Issue #9124 is on the v2 milestone; PR #11443 (a placeholder-email option) is a draft. The workaround is a synthetic address such as `<username>@users.invalid` per account, a column of fake data against ADR-0013.
- **Username plugin**: lowercases by default, 3 to 30 characters, `/^[a-zA-Z0-9_.]+$/` by default; uniqueness is checked with a read, then an insert (a race surfaces as a generic error, against ADR-0013 point 3); `POST /is-username-available` sits under the default limit of 100 per window, a cheap enumeration endpoint; sign-in does hash a dummy password for unknown users.
- **Admin plugin**: a nullable `role` text column (several roles comma-separated), `banned`, `banReason`, `banExpires`, `session.impersonatedBy`; `adminUserIds` bypasses role checks; HTTP endpoints `/admin/set-role`, `/admin/impersonate-user`, `/admin/set-user-password` and more, which must be left unmounted or disabled to keep role grants out of the product.
- **Phone-number plugin** (the later SMS sign-in): a `sendOTP` callback, 6 digits, 300 s, 3 attempts; sign-up by phone again needs `getTempEmail`, and the OTP's identifier is the plain phone number unless `storeIdentifier: "hashed"`.
- **Rate limiting skips Server Actions**: "Server-side requests made using `auth.api` aren't affected by rate limiting. Rate limits only apply to client-initiated requests" (spot-checked in its docs); its Origin check is skipped on that path too. Server Actions call `auth.api`, so both would be ours to build anyway. Its limiter keys on `ip|path` from `x-forwarded-for` (spoofable without `trustedProxies`), defaults to memory, and its docs say a 60 s window while the code says 10 s.
- **Sessions** store the token in plain text (unique column; the cookie carries it HMAC-signed), with `ipAddress` and `userAgent`; 7 days, refreshed daily.
- **Schema**: we could write the migrations ourselves (its CLI, now the `auth` package, emits SQL with unnamed constraints, no comments, no grants) and map names (`modelName`, `fields`, or Kysely's `CamelCasePlugin`; `user` is a reserved word in PostgreSQL); `generateId: "serial"` lets the database mint ids, returned as strings. A runtime schema check fails requests when the tables drift. Release 1.7.0 added a required `account.issuer` column and 1.7.3 removed it: "We did not meet that expectation in 1.7."
- **Hashing**: scrypt `N=16384, r=16, p=1` (about 32 MiB), replaceable. **Errors**: stable codes; `@better-auth/i18n` has Persian for 34 of 49 core codes and none of the plugins'. **Telemetry**: off by default, and 1.7.6 has no default endpoint. **Advisories**: 21 since 2025-01-01 (2 critical, 13 high), mostly in OAuth, OIDC, organisation and API-key plugins; those touching username, rate limits and cookies are fixed by 1.6.22.

**Auth.js v5** is still `5.0.0-beta.32` (2026-07-20); `@auth/core` 0.41.3 throws "Signing in with credentials only supported if JWT strategy is enabled", so credentials never get database sessions, and its docs recommend OAuth, magic links or passkeys instead. Better Auth's post: "we'll keep addressing security patches and urgent issues", and new projects should "start with Better Auth".

**iron-session 9.0.1** (2026-08-30, MIT): sessions are "signed and encrypted cookies … decoded … in a stateless fashion"; they "cannot be instantly invalidated", which fails sign-out-everywhere and a password change without a table beside it.

**Self-hosted identity servers**, each a second service with its own schema, upgrades and screens to translate, on a 4 GB VPS that already runs PostgreSQL, Next.js and the worker: Ory Kratos v26.2.0 (Apache-2.0, Go, PostgreSQL; usernames as identifiers through its identity schema; no published memory figure); Keycloak 26.7.4 (Apache-2.0, Java; "base memory usage … 1250 MB of RAM"); Zitadel v4.19.2 (AGPL-3.0 since v3, 2025; "around 512MB RAM", four cores recommended for password hashing); Authentik ("at least 2 CPU cores and 2 GB of RAM"). Whether their images can be pulled from inside Iran was not checked.

**SaaS is ruled out for Iran by its own terms:** Okta's master agreement forbids use "in a U.S. embargoed country or region (… currently Cuba, Iran, North Korea, Syria …)", and Auth0's support article "Sanctioned Country Traffic Blocked by Auth0" (updated 2026-04-16) says such users "will receive an access denied message"; Clerk's terms (2026-07-02) forbid use that would "violate any U.S. or international embargoes, economic sanctions, or export controls laws"; Supabase's forbid making the services "accessible from, any jurisdiction … to which export … is prohibited"; WorkOS's terms (2026-08-04) have no such clause, but as a US person it is bound by 31 CFR §560.204, which prohibits "the exportation … of any goods, technology, or services to Iran".

### 8. The first superadmin and role checks

**How mature products create the first administrator** (read here):

- Django's `createsuperuser` prompts for the password; with `--noinput` it reads `DJANGO_SUPERUSER_PASSWORD` from the environment, "Otherwise, no password will be set". There is no password argument.
- GitLab "generates a random password … stored in `/etc/gitlab/initial_root_password` for 24 hours. After 24 hours, this file is automatically removed for security reasons", and calls a password written into `gitlab.rb` "not recommended" because it is "in clear text".
- Keycloak's `kc.sh bootstrap-admin user` takes `--password:env PASS_VAR` or prompts when no parameter is given; the account it makes "should exist only for the duration necessary to perform operations needed to gain permanent and more secure admin access."
- CWE-214, "Invocation of Process Using Visible Sensitive Information": "A process is invoked with sensitive command-line arguments, environment variables, or other elements that can be seen by other processes on the operating system" (MITRE). Arguments also land in shell history. Standard input or a generated password avoids both.

**The database can refuse the grant itself.** PostgreSQL grants `INSERT` and `UPDATE` per column, and "A user may perform SELECT, INSERT, etc. on a column if they hold that privilege for either the specific column or its whole table" (PostgreSQL 18, `GRANT`), so a table-level grant must not be given. **Lab** (same PGlite run): with `GRANT INSERT (username, password_hash)` and `GRANT UPDATE (password_hash)` on `account`, the web role signed up a buyer whose `role` came from its default, changed a password, and got SQLSTATE 42501 ("permission denied for table account") both when an insert named `role = 'superadmin'` and when an update set it; a taken name failed with 23505 on `account_username_unique`, which maps to a Farsi message by name (`packages/db/src/database-errors.ts`). "The superadmin role is never granted through the product's own screens" can thus be a property of the web role, not a promise of the code.

**Role checks in Next.js 16.** Section 5: every Server Action is a public POST endpoint, layouts do not guard their pages, Proxy is optimistic only, and the Data Access Layer re-checks the session close to the data. CVE and advisory history for Proxy's predecessor is in section 3.

## Recommendation

Written so ADR-0020 can adopt it point by point. Where it departs from a standard, the departure is named.

1. **Our own code, no library.** Better Auth cannot create an account without an email until its v2 (#9124), checks username uniqueness by reading first, skips its rate limiter and origin check for `auth.api` calls (every Server Action), and stores session tokens in plain text; Auth.js gives credentials no database sessions; iron-session cannot revoke; identity servers are a second service on a 4 GB machine; the SaaS vendors exclude Iran by contract, and Auth0 blocks it. Password sign-in with two roles is a small surface: a password module, a session module, a throttle, a data-access guard and five Server Actions (sign up, sign in, sign out, change password, sign out everywhere). The password module sits where the web app and the bootstrap command can both import it (a `packages/*` package; ADR-0003's trigger, a second consumer). Revisit Better Auth when email becomes optional and OAuth, passkeys or a second factor are wanted.

2. **Hashing: Argon2id through Node.js's own `crypto.argon2`**, with `m=19456` (KiB), `t=2`, `p=1`, a 16-byte random salt and a 32-byte tag (OWASP's headline set; ASVS Appendix C), stored as a PHC string in `account.password_hash` (`$argon2id$v=19$m=19456,t=2,p=1$<salt>$<hash>`, standard Base64 without padding; a CHECK that it starts with `$argon2id$v=19$`).
   - Raise `engines` to Node.js 24 LTS, at least 24.19.0 (where it is marked stable), and the local machine with it; CI already runs 24, and ADR-0016 already needs more than this machine's 22.14.0. Official Node.js builds only (OpenSSL 3.2 or later); the server hashes once at start and refuses to run if that fails.
   - Verify by recomputing with the stored parameters and comparing with `crypto.timingSafeEqual`; after a successful sign-in, rehash when the stored parameters or key differ from the current ones. Never `argon2Sync`.
   - At most two hashes at a time per process (a semaphore): a request waits at most 5 s for a slot, then gets a Farsi "try again in a moment".
   - A pepper through Argon2's `secret` input (NIST: SHOULD), the key version in the PHC `keyid` parameter, the key kept like the phone-hash key of ADR-0013 point 8 and never in the database or its backups. Losing every key makes every password unusable, so it is backed up with the other secrets. It can also be added later without a migration, by rehashing at sign-in.
   - Not `@node-rs/argon2` 2.1+ (an engine seven weeks old); `argon2` 0.45.1 (the reference C code) is the fallback if a host cannot run Node.js 24. Not bcrypt (72 bytes, 36 Persian letters).

3. **Password policy** (NIST SP 800-63B-4 §3.1.1.2, ASVS 6.2):
   - **Buyers**: 15 to 128 characters counted as code points after normalisation; any characters, spaces and Persian included; no composition rules, expiry, hints or security questions; paste, password managers (`autocomplete="new-password"` and `"current-password"`) and a show-password button allowed; changing it needs the current password.
   - **Superadmin**: generated by the bootstrap command (24 characters from a 32-symbol alphabet, 120 bits), or, when typed, at least 20 characters and the same checks.
   - **Normalisation, before hashing and before the blocklist**: NFC (NIST); non-ASCII spaces to U+0020 (RFC 8265); Arabic ي (U+064A) and ى (U+0649) to ی (U+06CC), ك (U+0643) to ک (U+06A9), Persian and Arabic-Indic digits to ASCII, as the search normaliser and ADR-0014 already do. No trimming and no case folding. This departs from ASVS 6.2.8 ("exactly as received"), on purpose: the same password typed on a phone and on a Windows machine with the legacy layout would otherwise differ. It is permanent for every stored hash.
   - **Blocklist, exact whole-password match, reason given in Farsi**: the SecLists union (NCSC 100k, Pwdb and xato top million) filtered to 15 characters or more, 16,135 entries committed as a small file; `carshenas`, `karshenas`, `کارشناس`, the username and its variants with digits; each also checked after mapping Persian-layout keystrokes back to Latin (a Latin password typed with the Persian layout on) and after lowercasing. No call to Have I Been Pwned or any service abroad.

4. **Usernames**: 3 to 30 characters of `a–z`, `0–9` and `_`, starting with a letter (Telegram's alphabet); typed capitals are lowercased and Persian digits made Latin before the check; stored lowercase with a CHECK (`account_username_format`) and a UNIQUE constraint (`account_username_unique`) whose violation maps to a Farsi "this name is taken"; `admin`, `administrator`, `root`, `sa`, `support`, `system`, `carshenas`, `karshenas` and similar names refused (ASVS 6.3.2). A username is not secret, is never shown to other buyers and is never logged: people type their names into it, and sometimes their password (add `username` to the log sanitiser's names).

5. **Session token**: 32 bytes from `crypto.randomBytes` (256 bits; ASVS asks 128), base64url in the cookie only. The database stores `token_sha256 bytea` (32 bytes, UNIQUE) and looks the session up by it, the pattern `saved_search.link_token_sha256` already uses; Lucia's current id-plus-secret with a constant-time comparison is an equally good alternative. Table `account_session`: `id` (identity), `account_id` (FK, `ON DELETE CASCADE`, indexed), `token_sha256`, `created_at`, `last_seen_at`, `expires_at` (absolute), `idle_expires_at` (null for buyers); no address or user agent. A new token at every sign-in (fixation); the role is read from `account` on every request, never copied into the session.

6. **Lifetimes, renewal and ending sessions**:
   - **Buyer**: 30 days from sign-in (NIST AAL1: "SHOULD be no more than 30 days"), no inactivity limit (NIST: MAY), no sliding renewal, so no cookie ever has to be rewritten while a page renders. `last_seen_at` is refreshed at most once an hour.
   - **Superadmin**: 12 hours from sign-in and 1 hour of inactivity (`idle_expires_at` pushed forward at most every 5 minutes, never past `expires_at`); a browser-session cookie.
   - The database decides validity; the cookie's lifetime only tidies the browser (NIST: "SHALL NOT be relied upon").
   - Sign-out deletes the row and expires the cookie; "sign out everywhere" deletes all the account's rows; a password change deletes every other session and replaces the current one (OWASP; stricter than ASVS 7.4.3's option); suspending an account deletes its sessions (ASVS 7.4.2); the bootstrap command deletes them when it changes a role or password; a daily worker job deletes expired sessions, device tokens and spent throttle rows.

7. **Cookie**:
   - **Production** (the site's origin is https): `__Host-session=<token>; Path=/; Secure; HttpOnly; SameSite=Lax`, with `Max-Age=2592000` for buyers and none for the superadmin; never `Domain`. HSTS on the host (CS-37).
   - **Development and tests over http on loopback**: `session=<token>; Path=/; HttpOnly; SameSite=Lax`, without `Secure` and the prefix, because WebKit on Linux, which CI runs as the `iphone` project, refuses every `Secure` cookie over http (lab).
   - The choice comes from a new required setting, `CARSHENAS_ORIGIN` (`https://…` in production, `http://127.0.0.1:3100` in the e2e suite), not from `NODE_ENV`, since the e2e suite runs a production build over http. An http origin whose host is not `localhost`, `127.0.0.1` or `[::1]` stops the server at start; the server reads only the cookie name it would set.

8. **Cross-site request forgery**:
   - Every change of state is a Server Action; no GET changes anything; sign-out is a form post.
   - Next.js's origin check stays on, with no `allowedOrigins`; the reverse proxy passes the public `Host`.
   - Our own `assertSameOrigin()` opens every mutating action, inside the wrapper that also authenticates: accept `Sec-Fetch-Site: same-origin`; without that header, require `Origin` to equal `CARSHENAS_ORIGIN`; refuse when both are missing. This closes Next.js's pass-through of a request without `Origin` (OWASP: block when neither header is present) and refuses a `null` origin whatever the framework does (CVE-2026-27978). Any future mutating Route Handler gets the same check.
   - `SameSite=Lax` written out, since Firefox and Safari do not default to it.
   - No synchronizer token: NIST's "POST/PUT content SHALL contain a session identifier" is not met, a named departure; revisit if an origin-check bypass appears.

9. **Throttling in PostgreSQL**: one table, `auth_throttle`: `id` (identity), `scope` (CHECK: `sign_in_account`, `sign_in_device`, `sign_in_address`, `sign_up_address`), `subject_hmac bytea` (32 bytes: HMAC-SHA-256 under its own versioned server key of the normalised username, whether or not the account exists; of a device token; or of the client address, IPv4 /32 or IPv6 /56), `key_version`, `failures`, `window_started_at`, `next_attempt_at`, and UNIQUE `(scope, subject_hmac)` (`auth_throttle_subject_unique`). No usernames or addresses are stored.
   - **Per account name, for clients without a device token**: an attempt first takes a lease in one statement (`UPDATE … SET next_attempt_at = now() + interval '10 seconds' WHERE … AND next_attempt_at <= now() RETURNING failures`, after `INSERT … ON CONFLICT DO NOTHING`), so guesses at one account never run in parallel. A failure adds one and sets the next attempt: no wait for the first 5 failures, then 30 seconds doubling up to 1 hour (NIST's example). A success deletes the row (NIST: disregard earlier failures). At 100 consecutive failures, password sign-in for that account is disabled for clients without a device token (`account.password_disabled_at`, NIST §3.2.2) until the superadmin (for a buyer, CS-40) or the bootstrap command (for the superadmin) clears it; with the waits, that takes about four days of steady attempts.
   - **Per device** (OWASP device cookies): a successful sign-in also sets `__Host-device` (named and flagged like the session cookie of point 7; a random token stored hashed in `account_device` with the account id, 400 days, the most browsers keep, deleted on a password change). Attempts that present it count on their own row with the same waits, and neither the account-wide wait nor the disable applies to them. The owner keeps signing in while someone hammers `pedram` (ASVS 6.3.1). It ships with the waits: without it, growing waits are the lockout the Auth book warns "can be easily abused to indefinitely lock out legitimate users".
   - **Per address**: at most 100 failed sign-ins per address per hour across all names (generous, because carrier-grade NAT shares addresses), and at most 20 sign-up attempts per address per hour, which also bounds how fast usernames can be enumerated through sign-up. Over the limit, the request waits for the window's end without hashing.
   - The client address is the rightmost `X-Forwarded-For` entry, written by the one reverse proxy we run (`proxy_set_header X-Forwarded-For $remote_addr`, or nginx's real-IP module behind a CDN), with Next.js listening on loopback only (CS-37); without a proxy, Next.js fills the header from the socket.
   - Every limit is a setting, so the e2e suite (every worker signs in from 127.0.0.1) raises the address limits except in the throttle's own tests.
   - An unknown username takes the same path: the throttle keyed by the typed name and a verification against a dummy hash with the same parameters. Every failure answers «نام کاربری یا رمز عبور درست نیست» and every throttled answer says when to try again, for existing and unknown names alike. Sign-up must say that a name is taken; the sign-up limit is the defence.
   - Logs: one line per attempt with the outcome, the account id when known and the throttle scope; never the typed username, the password, a token or an address (OWASP Logging: "Always log: Authentication successes and failures").

10. **The first superadmin and role checks**:
    - `account.role` is text with a CHECK (`buyer`, `superadmin`) and default `buyer`. The web role gets column privileges only (`INSERT (username, password_hash)`, `UPDATE (password_hash, …)`), never `role`, and neither does CS-40's admin role: the database refuses a grant from the product (lab: 42501).
    - A command, `pnpm account:superadmin --username pedram`, connecting as `carshenas_migrate`, creates or promotes the account. It generates the password and prints it once to the terminal, or reads one line from standard input with `--password-stdin`; never from an argument or the environment (CWE-214). One transaction: upsert on `account_username_unique` setting `role = 'superadmin'` (the password only on creation or with `--reset-password`); append to `account_role_change` (append-only, ADR-0013 point 7: account, from and to roles, `changed_by`, reason, time) when the role changed; clear the account's throttle and disable; delete its sessions when the role or password changed. Running it again changes nothing. It becomes a step of "Bootstrapping a new server" in `docs/runbooks/local-database.md`; the e2e setup makes its own superadmin with a random password per run.
    - `src/server/auth/` offers `currentAccount()` (React `cache`; one query joining session and account), `requireAccount(next)` (redirects to sign-in with a checked `next`) and `requireSuperadmin()` (calls `notFound()` for everyone else, as CS-40 wants). Every admin page, admin Server Action and admin query calls it itself; neither a layout nor `proxy.ts` is ever the guard. A test calls each admin action and query without a superadmin session and expects not-found.
    - After sign-in, a superadmin goes to the admin dashboard; a buyer goes to `next` when it is a path on this site (one leading `/`, not `//` or `/\`), otherwise home.
    - The session is read inside `<Suspense>` (Cache Components), never at a layout's top level, and no token reaches a cache key.

**Trade-offs accepted.** A 15-character minimum costs sign-ups some effort; a hand-rolled design means we own its review, mitigated by a small surface and tests of every rule above; the named departures (ASVS 6.2.8's "exactly as received", NIST's CSRF token, NIST's non-persistent session secrets for buyers, ASVS 6.3.3's second factor for the superadmin) are recorded in the ADR.

**What would change this.** WebKit on Linux accepting `Secure` cookies on loopback (drop the http cookie); a host that cannot run Node.js 24 (`argon2` 0.45.1); evidence of credential stuffing or of lockout abuse despite device tokens (a bot challenge reachable from Iran); Better Auth v2 with optional email plus a need for OAuth, passkeys or a second factor; phone and SMS sign-in, which brings a recovery channel.

**Open questions for the owner.**

1. Buyers' minimum length: 15 (NIST's SHALL for a password-only account, recommended) or 8 (ASVS level 1's floor), which needs the 915,000-entry blocklist (3.4 MB gzipped) instead of 16,000?
2. Forgotten passwords: with no email or phone there is no self-service recovery, and the superadmin cannot tell the real owner of a buyer account from anyone else. Accept lost accounts until phone sign-in arrives, or show a one-time recovery code at sign-up (NIST's saved recovery codes, at least 64 bits)?
3. Latin-only usernames (recommended, as on Telegram) or Persian letters too, which brings confusable letters and the ی/ي question into identities?
4. Folding Persian digits and Arabic letters before hashing (recommended): once passwords are stored, it cannot be undone.
5. Buyers stay signed in for 30 days across browser restarts (recommended) or only for the browser session (NIST's SHOULD)?
6. Node.js 24 on the owner's machine and the server, and the pepper from day one or later?
